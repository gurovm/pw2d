## Medium issues (fix before the first production apply / first calibration export)

### MEDIUM-1 — an exception inside the per-row transaction aborts the whole batch with no table, no summary, and a stack trace instead of the spec'd exit contract

**Where:** `app/Actions/ApplyProductEvaluations.php:120-132` — `DB::transaction(...)` has no `try/catch`;
`execute()` (:34-46) and the command (`ApplyProductEvaluations.php:56-64`) don't catch either.

**Mechanism:** `FinalizeProductEvaluation::execute()` calls `AiService::matchProduct()` (:97), which calls
`GeminiService::generate()`. That throws a plain `\Exception` on any non-2xx after the 429-only retry
(`GeminiService.php:77-93`) and lets `ConnectionException` (timeout, DNS) through untouched — the
`retry(... when: RequestException && 429)` clause never retries a timeout. A deadlock / lock-wait
`QueryException`, or a `brands` race with a queue worker, behaves the same. `DB::transaction` rolls this
product back (correct) and rethrows; the throw leaves `applyRow()` → `execute()` → `handle()` →
`finally { tenancy()->end() }` → artisan prints the trace and exits 1.

**Concrete scenario:** 93-row lavalier apply, row 41 is a Hollyland product; the site model returns a 503
(or the request times out at 15 s). Rows 1–40 are committed and invisible to the operator (no table
printed); rows 42–93 are never attempted. Re-running is safe (idempotent — rows 1–40 skip) but the operator
has no record of what landed, and if the cause persists row 41 kills every re-run at the same point.
The spec contract (§2 T4: "table … summary … exit 1 if errors > 0") is not met for this class of failure.

**Fix (5 lines, in `applyRow()`):**
```php
try {
    return DB::transaction(function () use (...) { /* unchanged */ });
} catch (\Throwable $e) {
    Log::error('ApplyProductEvaluations: row failed', ['product_id' => $productId, 'source' => $source, 'error' => $e->getMessage()]);
    return $this->row($productId, 'error', 'apply failed: ' . $e->getMessage());
}
```
The row lands in `errors`, the batch continues, exit is 1 at the end — exactly the spec's error semantics.
Test: fake Gemini with `Http::response([], 503)` for a brand that has a processed product, plus one
ignored row after it; assert the ignored row is still applied and exit is 1.

### MEDIUM-2 — the spec's "every category feature present" rule is not enforced at apply time; a row that silently drops a feature produces a permanently half-scored *processed* product

**Where:** `app/Actions/ApplyProductEvaluations.php:108-113` checks only that every *scored* name exists on
the category (spec §2 T4 step 3). Spec §2 T1's strictness rule says the four-value enum **and** "the
'every category feature present' rule are enforced at apply time for file rows (T4)". The enum is
enforced (:71-73); completeness is not. The runbook already promises it to the operator
(`docs/ops/bouncer-session.md:67`: "Every feature listed for the category must appear in `features`").

**Consequence:** `features: {}` or a 7-of-8 map passes validation, `FinalizeProductEvaluation` writes
`status = null` (:172), and `applyFeatureScores()` writes whatever is present (:247-268). The product is
now "processed": `ProductScoringService.php:58-59` just skips the missing feature (`if ($fv === null)
continue;`), so it ranks on a partial weighted average and shows a gap in the comparison table, and
nothing re-evaluates it — runbook step 8 is the extension *listing-health* rescan, not a feature rescan.
A subagent omitting one key across a batch of 20 is precisely the failure this rule exists to catch;
a misspelled key is caught (:110), an omitted one is not.

**Fix (in `applyRow()`, after the unknown-name loop; use the *raw* row so an explicit `null` — which the
VO drops, and which Gemini's own contract allows — still counts as present):**
```php
if (!$eval->isIgnored()) {
    $missing = array_diff($knownFeatures, array_keys($rawRow['features']));   // features is a validated array here
    if ($missing !== []) {
        return $this->row($productId, 'error', 'missing feature(s): ' . implode(', ', $missing));
    }
}
```
Note the existing test `a_row_for_an_already_processed_product_is_skipped` uses `features: []` and will
still pass (skip happens at step 2, before step 3).

### MEDIUM-3 — the blind `--status=processed` export leaks the stored name/brand/tier/scores of up to `--anchors` of the very products under test, contaminating the T5 calibration gate

**Where:** `app/Actions/ExportPendingProducts.php:101-111` (products: processed, ordered by id, optional
limit) and `:136-163` (anchors: processed with feature values, top-N by `amazon_reviews_count`). Nothing
excludes the exported ids from the anchor set.

**Concrete scenario:** runbook trust-gate command
`export-pending pw2d <slug> --status=processed --limit=50`. The five most-reviewed products in the
category are almost certainly inside the first 50 by id (or all of them, for a category with ≤ 50
processed products). The file then contains, for the same product, `anchors[].name = "DJI Mic 2"`,
`brand = "DJI"`, `price_tier = 2`, `features = {"Audio Quality": 85, …}` **and**
`products[].raw_title = "DJI Mic 2 Wireless Lavalier …"`, `url = …/dp/B0CG…`. Any evaluator (a subagent
included) will align them and copy the numbers — the runbook's "do not copy their numbers" is not a
control. 5 of 50 rows (10 %) then score perfect agreement, which is enough to move a gate whose
thresholds are ≥ 95 % / ≥ 98 % / MAD ≤ 5. The gate is what decides whether the session becomes the
*first* path (§6), so the bias is in the dangerous direction.

**Fix (one argument):** compute `$products` first (already the case), then
`$this->buildAnchors($category, $anchorsCount, $isProcessed ? $products->pluck('id')->all() : [])` and
`->when($excludeIds !== [], fn ($q) => $q->whereNotIn('id', $excludeIds))` in the anchor query. Anchors
then come from processed products *outside* the exported set; a category with nothing left yields `[]`,
which the file format already supports. Add `meta.anchors_exclude_exported: true` so the T5 diff can
assert the export was clean. Test: 3 processed products, `--status=processed --limit=3 --anchors=5` →
`anchors === []`; with `--limit=2` → the one anchor is the product not in `products[]`.

### MEDIUM-4 — a still-queued `ProcessPendingProduct` job silently overwrites (or re-fails) a product the session has just finalized; T4 has no guard and the runbook's fallback claim is wrong

**Where:** `app/Jobs/ProcessPendingProduct.php:43-50` — on `status !== 'pending_ai'` the job logs
"unexpected status, processing anyway" and **continues**; on the third failed attempt it writes
`status = 'failed'` (:89-90) unconditionally. `ApplyProductEvaluations` checks status once, outside the
transaction (:95-98), and has no notion of the queue. `docs/ops/bouncer-session.md:16` says
"wait until 0, **or accept that jobs will fail into 'failed'**" — that second half is a mechanism claim
that the code contradicts (2026-08-28 lesson: verify "leave it alone" rationales).

**Concrete scenarios (both need a job in `jobs` at apply time — retry backoff is 10 s / 60 s / 300 s, a
worker restart or `queue:retry` re-queues, an import in another category dispatches fresh ones):**
(a) quota recovered — the job re-runs Gemini on the session-finalized product and overwrites name, slug,
brand, summary and every feature value with Gemini's answer, plus a second `ai_usage` row; the session's
work and its `claude-code-session` accounting are silently replaced. (b) quota still walled — attempt 3
sets the finalized product back to `status = 'failed'`; it reappears in the next export, passes the T4
status guard, and is re-applied against a product whose `name` is now the cleaned name (so
`matchProduct()` is asked about the wrong title).

**Fix (3 lines in the command, before `execute()`, skipped under `--dry-run`):**
```php
$queued = DB::table('jobs')->where('payload', 'like', '%ProcessPendingProduct%')->count();
if ($queued > 0 && !$this->option('force')) {
    $this->error("{$queued} ProcessPendingProduct job(s) still queued — let the queue drain or pass --force.");
    return self::FAILURE;
}
```
and delete the "or accept that jobs will fail into 'failed'" clause from runbook step 2 (T6 file; out of
this review's scope but the claim guards this write path). The `jobs` payload is a serialized command
class name, so the LIKE is reliable on the database driver this project uses.

  (`2026_03_26_000001_create_product_offers_table.php:19`), so the fallback only fires for a processed
  product with **no offers at all** — but then it emits the stored, AI-normalized `name` into a file whose

  Same file, `ratingNote()` docblock (:213-218) claims the AI never writes `amazon_rating`; the finalize

  is AI-writable. Not a leak in practice; correct the comment.
- **LOW-7 — silent empty export on `json_encode` failure / `--limit=abc`.**
  `Commands/ExportPendingProducts.php:68-71` writes `file_put_contents($path, false)` and prints
  "Exported N products" if `json_encode` returns `false`; add `JSON_THROW_ON_ERROR`. `:55` casts a
  non-numeric `--limit` to `0` → `limit(0)` → an empty export with exit 0; reject non-digits.
- **LOW-8 — lock-hold across the transaction: assessed, acceptable, no change recommended.** In the
  scored path nothing is written before `matchProduct()` (`FinalizeProductEvaluation.php:68-97`: ignore
  branch returns, name cap is pure), and `matchProduct()` itself only reads before its HTTP call
  (`AiService.php:227-248`), so during the Gemini round trip (≤ 15 s × up to 3 on 429) the transaction
  holds a consistent-read snapshot and **no row locks**. Locks are taken afterwards — product row X-lock
  (:164), optional `brands` insert (:159), next-key locks over the tenant's `ai_matching_decisions` range
  from the LIKE delete (:186-194), `product_feature_values` rows (:259) — and are then held across the
  image download (`:340`, `Http::timeout(15)`) and `cwebp`, i.e. ≤ ~16 s. A concurrent worker's
  `AiMatchingDecision::create()` / same LIKE delete for the same tenant blocks for that long and then
  proceeds (default `innodb_lock_wait_timeout` is 50 s); the worker runs autocommit so it never holds a
  lock T4 waits on — no deadlock cycle. For an operator batch of ~100 on a weekend when the queue is
  idle this is fine. **Do not hoist the AI call**: it would change the shared action for the Gemini path
  and buys nothing, since no locks are held during it. If this ever matters, the image download is the
  thing to move out of the transaction, not `matchProduct()`.
- **LOW-9 — `pending_ai` window inside the transaction.** Independent of MEDIUM-4, re-reading the product
  with `lockForUpdate()` and re-checking status inside the transaction is a cheap belt-and-braces against

  silently becomes processed-only (`:43`). Validate both.
- **NIT** — `FinalizeProductEvaluation` log lines keep the `ProcessPendingProduct:` prefix with `source`
  added on three of five (`:74, :127, :202`); the two rejection lines (`:144, :227`) lack `source`.
- **NIT** — LOW-4 of the previous review asked for `(string)` casts on the `parse_url()` consumers as well

## Verified correct (mechanism checked against source, not the builder's report)

**Write path — `ApplyProductEvaluations`**
1. Tenant ownership: `Product::withoutGlobalScopes()->where('id', …)->where('tenant_id', $tenant->id)` (:85-89);
   a row naming another tenant's id resolves to `null` → `skipped`, nothing written (test
   `a_row_for_another_tenants_product_is_skipped` asserts the foreign product is untouched).
2. Status guard: `in_array($product->status, ['pending_ai', 'failed'], true)` (:95) — `null`, and any other
   value, skip with the reason in `detail`.
3. Feature names validated against the product's category (`:102-113`); category loaded with
   `withoutGlobalScopes()->with('features')` — the `features` eager-load is tenant-scoped by `Feature`'s
   `BelongsToTenant`, same tenant, so correct.
4. Four-value enum enforced here and only here (`:71-73`, `ProductEvaluation::VALID_REASONS`); an empty
   reason (`''` from a missing key) is rejected as `unknown reason ""`.
5. One `DB::transaction()` per product (`:120`); the transaction returns the outcome row. Rollback on throw
   discards product/brand/feature/decision writes, observer-dispatched `jobs` rows (same connection), and
   the `ai_usage` row (recorded after finalize, `:123`); only a stored image file could survive, and only
   if `$product->update(['image_path'])` failed after the file write.
6. `--dry-run`: steps 1–3 are reads only; `predictedRow()` (`:115-117`) returns before the transaction;
   no `Log::` call, no `ai_usage`, no HTTP (`Http::assertNothingSent()` pinned), `tenancy()->initialize()`
   writes nothing.
7. Idempotency: re-run → `scored`/`ignored`/`rejected` rows are `status = null` → skipped; `merged` rows
   are `forceDelete`d → "not found for this tenant" → skipped; second run records no `ai_usage`
   (pinned).
8. Exit code: `errors > 0 ? FAILURE : SUCCESS` (`Commands/ApplyProductEvaluations.php:64`); skips alone
   exit 0 (pinned). File/tenant/shape failures exit 1 before tenancy is initialized.
9. All `Product` writes in the finalize path are model-level (`update()`/`forceDelete()`), so
   `ProductObserver::saved()/deleted()` fire under T4 exactly as on the Gemini path;
   `AuditLandingPageFreshnessJob::dispatchForProduct()` uses an explicit `tenant_id` (`:72`).

## Praise
- The write path is defensive in the right order: schema → enum → id → tenant → status → category →
  features, each failure a *row* outcome rather than a throw, and the explicit `tenant_id` predicate is
  there even though the global scope would already apply — the project's safety-net rule applied, not
  just cited.
- The snapshot was captured with a throwaway test *before* touching `AiService.php`, and the pinned test's
  docblock tells the next person not to regenerate it against refactored code. That is the correct way to
  prove "byte-identical", and it made this review's provenance check possible.
- The `estimateCost()` short-circuit is placed before the no-token rule with a comment that explains why
  the order matters (a metered call with missing token counts must still be `null`, not `$0`). Small,
  correct, documented.
- `priceNote()` in the export deliberately recomputes from price + thresholds instead of reading the
  stored tier, with the reason stated — the blind contract was thought through at the field level, which is
  why MEDIUM-3 is the only leak left.
