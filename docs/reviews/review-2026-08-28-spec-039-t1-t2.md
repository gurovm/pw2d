## Critical Issues (must fix)

### HIGH-1 — `fromArray($result['parsed'])` turns Gemini's non-JSON replies into an uncaught `TypeError`; the product is stranded at `pending_ai` instead of `failed`

**Where:** `app/Jobs/ProcessPendingProduct.php:78` → `app/Support/ProductEvaluation.php:60`
(`fromArray(array $raw)`), with `GeminiService::generate()` typed `parsed: ?array`
(`app/Services/GeminiService.php:33`, `:120` is a bare `json_decode($content, true)`).

**Old behaviour (old :77-91):** `$parsed = null` → `($parsed['status'] ?? null)` is silent under `??` →
`empty($parsed['name'])` is true → `throw new \Exception('Invalid AI response: …')` → caught by
`catch (\Exception $e)` (old :229) → logged as `ProcessPendingProduct: failed` → rethrown for retry, and on
the third attempt `$product->update(['status' => 'failed'])` (old :236).

**New behaviour:** `ProductEvaluation::fromArray(null)` throws `TypeError` (`array` parameter, null given —
no coercion exists for null → array in either typing mode). `TypeError` extends `\Error`, not `\Exception`,
so the job's `catch (\Exception $e)` at new :83 does not see it. It propagates to the worker, which catches
`Throwable` (`vendor/laravel/framework/src/Illuminate/Queue/Worker.php:488`) and retries per `$tries`; after
the third attempt the job lands in `failed_jobs`, but neither the `ProcessPendingProduct: failed` log line
nor the `status = 'failed'` write ever executes. The product stays `status = 'pending_ai'` — invisible to
Filament's "Retry Failed" (`ListProducts.php:50` filters `status = 'failed'`) and mis-counted by
`ProductStatsWidget`.

**Is it reachable with real Gemini?** Yes, on the STOP path that `GeminiService` does not guard:
a `SAFETY`/`RECITATION`/`OTHER` finish with no text parts (`$raw = ''` → `json_decode('')` → `null`), or a
prose preamble before the JSON object (`json_decode` → `null`), or a bare JSON string/number (→ scalar,
same `TypeError`). `MAX_TOKENS` and HTTP errors are already `\Exception`s and are unaffected.

**This contradicts the spec's own invariant** (§2 T2: "the retry/`failed` semantics at the catch block are
unchanged") and the job's comment at new :74-77 ("both are caught below with identical retry semantics").

**Fix (3 lines, in the value object so T4 gets it too — T4 rows from a hand-edited file can be anything):**
```php
public static function fromArray(mixed $raw): self
{
    if (!is_array($raw)) {
        throw new InvalidProductEvaluation('payload', 'must be a JSON object');
    }
    …
```
**Test to add** (`ProcessPendingProductEvaluationTest`): fake Gemini returning
`['text' => 'Sorry, I cannot evaluate this product.']` with `finishReason: STOP`, then
`expectException(\Exception::class)` around `handle()` (sync driver: `attempts()` is 1 < 3, so the catch
rethrows). Against the current code this test fails with `TypeError`, which is the proof.

## Suggestions (recommended improvements)

### MEDIUM-2 — an `ignored` verdict with an off-list `reason` now fails the product instead of ignoring it

**Where:** `ProductEvaluation.php:69-73` (`buildIgnored`: reason must be a string in `VALID_REASONS`).
**Old:** old :80-87 accepted any value, including a missing one (`'reason' => $parsed['reason'] ?? ''`), and
marked the product ignored. The reason is used nowhere except that log line.
**Scenario:** the prompt says "return EXACTLY" (`AiService.php:58/:62/:65`) but LLMs drift —
`"accessory"`, `"accessory_or_bundle: replacement cable"`, `"bundle"`. Each such reply now costs three
admin-model calls and ends at `status = 'failed'`, discarding a correct Bouncer rejection; the product then
shows up in the T3 export as a `failed` row for the session to re-judge, which is the exact work the gate
already did. The existing `?? ''` is evidence the original author expected missing reasons.
**Fix options:** (a) relax `buildIgnored` to `is_string($reason) && $reason !== ''` (cap ~100 chars), keep
`VALID_REASONS` as a documented constant, and let T4 enforce the enum for file rows (where an `error` row is
cheap and visible); or (b) keep the enum but have the job map an off-list reason to the ignore branch with a
warning. (a) is simpler and keeps the VO shared. Only `wrong_category` has routing significance
(`FinalizeProductEvaluation.php:66`), so the enum buys nothing on the Gemini path.

### MEDIUM-3 — free-text caps and the feature `reason` requirement reject payloads the old path stored

**Where:** `ProductEvaluation.php:98` (`ai_summary` required, ≤ 600), `:188` (`reason` key must exist),
`:200` (`reason` non-empty string ≤ 300), `:188` (bare-numeric feature entry rejected).
**Old:** old :178 `'ai_summary' => $parsed['ai_summary'] ?? null`; old :211-212 accepted a bare number and a
missing/null `reason`. Both DB columns are `text` (`ai_summary`: schema line 17; `explanation`: nullable
`text`, schema line 35), so nothing at the storage layer ever rejected long text.
**Scenario:** one 320-character "one sentence" reason on one of eight features → the whole product fails
after three paid attempts. A "brutal 2-sentence summary" over 600 characters does the same. Frequency is
low but non-zero; the failure cost is high (3× admin-model, then manual re-work).
**Internal contradiction:** the class's own `@param array<string, array{score: float, reason: ?string}>`
(`:46`, `:167`, `:251`) says `reason` is nullable; the code at `:188-202` rejects null, missing and empty.
**Fix:** make `reason` optional/nullable (matching the docblock and the old loop), and truncate free text
with `mb_substr` at the cap rather than throwing — the Bouncer path is already lossy by design
(`capProductName()` truncates rather than rejects). Keep `ai_summary` required non-empty (it is rendered).
The bare-numeric entry can stay rejected on this path (the prompt never asks for it) — note it only.

### LOW-4 — `strict_types=1` on the moved image helper converts two coercive-mode deprecations into `TypeError`s that escape both catch blocks

**Where:** `FinalizeProductEvaluation.php:318` (`$host = parse_url(…, PHP_URL_HOST)` is `?string|false`)
feeding `str_contains` at `:326` and `str_ends_with` at `:328`; `:357` `basename(parse_url(…, PHP_URL_PATH))`
where the path can be `null`. The old job had no `declare(strict_types=1)`, so these were "passing null to
non-nullable internal parameter" deprecations returning `false`/`''`; under strict mode they are
`TypeError`s. The helper's `catch (\Exception $e)` at `:371` and the job's at new :83 both miss `\Error`.
**Scenario:** the error would fire *after* the product is fully written (status null, scores saved), so the
retry re-runs Gemini three times and regenerates the slug three times for a product that is already done.
**Reachability:** low — `image_url` is validated `nullable|url` on all three ingress paths
(`BatchImportRequest.php:52`, `ProductImportRequest.php:38`, `OfferIngestionController.php:42`), which
guarantees a host; a host-only offer `url` with no path is theoretical for `/dp/…` URLs.
**Fix:** the helper is documented "non-fatal" — make it `catch (\Throwable $e)`, and `(string)`-cast the two
nullable values.

### LOW-5 — `price_tier` strictness can hard-fail where the old path silently wrote a bad tier

**Where:** `ProductEvaluation.php:132` (`in_array($value, [1, 2, 3, '1', '2', '3'], true)`).
`2.0` (a JSON `2.0` decodes to float) and `0`/`4` now throw; old :179 wrote the raw value (0/4 → an invalid
tier, later repaired by `products:recalculate-tiers`). Neither is good. **Fix:** coerce — numeric, integral,
in 1..3 → `(int)`, otherwise `null` (falls back to the product's own tier at `:164`), which is strictly
better than both.

### LOW-6 — forward notes for T3/T4 (not T2 defects; recorded so the next builder does not rediscover them)

- `execute()` assumes `$product->offers.store` (`:102`, `:309`) and `$category->features` (`:245`) are
  eager-loaded; the job does this at new :32-33. T4 must load both or every row lazy-loads (N+1 across a
  93-row apply, and `best_offer` needs `store` for its tiebreak).
- `execute()` performs an HTTP call (`matchProduct`, `:93`) — T4's "own DB transaction per product" will
  hold a transaction open across a Gemini round trip (up to 15 s). Acceptable at this scale, but it should be
  a conscious choice; observer-dispatched jobs (`ProductObserver::saved`) go through the same transaction on
  the database queue driver, which is actually desirable.
- Log lines inside the action keep the `ProcessPendingProduct:` prefix (`:71`, `:123`, `:139`, `:197`,
  `:221`). Required for Gemini-path identity now; from T4 they will be misattributed. `$source` is the
  natural fix, but changing message text/keys is a Gemini-path change — do it in T4 deliberately.
- Test gap, does not hide a defect: the docblock of `FinalizeProductEvaluationTest` says the moved branches
  are "covered end to end" by four suites. The merge branch (offer transfer, same-store-cheaper rule,
  `forceDelete`) and the pre-existing-rejection branch have **no** test that runs the job:
  `BrandNormalizationTest` re-implements the brand logic inline and `AiMatchProductTest` tests
  `matchProduct()` alone. Identity there rests on the line-by-line trace below (which is exact). A merge test
  is cheap: seed an `AiMatchingDecision` `is_match = true` for the raw title (no HTTP needed), two offers
  (one same-store cheaper), assert transfer + update + delete + `Merged`.

### NITs
- `execute(… string $source)` is accepted and unused (`:63`, documented at `:57-61`). Fine for now; see LOW-6.
- The job now builds two `AiService` graphs per run (`app(AiService::class)` at new :69 and the one injected
  into `app(FinalizeProductEvaluation::class)` at new :82). Stateless apart from the per-instance
  unpriced-model warning dedupe already noted in the Spec 038 review (L2). Harmless.
- `declare(strict_types=1)` is still absent from both job files — pre-existing (Spec 038 review N3) and
  correctly *not* added here (`best_price` coercion at the `evaluateProduct(?float …)` boundary).
- `requiredString()` does not `trim()`; identical to old (`Brand::create` got the raw string). Trimming
  name/brand in the VO would only affect padded values and is a small improvement for the session producer.
- `validatedFeatures()` rejects non-string keys (`:178`); PHP turns a purely numeric feature name into an
  int key. No such feature exists. Note only.
- `ProductEvaluation` accessors return `?string` for `name()/brand()/aiSummary()`; the action passes them to
  `string` parameters (`:307`) and `mb_strlen` (`:82`) — non-null by construction on the scored path, but a
  static analyser will flag it. A `scoredName(): string` style accessor or an `assert()` would quiet it.

## Praise
- The extraction is a genuine move, not a rewrite: every branch, log message and context key matches the
  old file line for line, and the `status`-key compatibility finding (documented on the class and in the
  builder memory) is exactly the kind of "fixtures describe truth" check the 2026-08-22 lesson asks for.
- `rejectFromCategory()` uses model-level saves and its test asserts the observer's side effect rather than
  just the column values — the 2026-08-21 mass-update lesson applied, not just cited.
- `applyFeatureScores()` closes todo L2 with the rescan-path zero-score test placed on the only caller where
  that guard is still reachable; the lesson entry explaining why is correct.
