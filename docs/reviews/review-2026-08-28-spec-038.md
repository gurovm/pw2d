## MEDIUM

### M1 — `ProductImportController` existing-product path re-manufactures the exact stuck state the migration cleans up

**Where:** `app/Http/Controllers/Api/ProductImportController.php:134` (sets `'status' => 'pending_ai'`
unconditionally on any existing-product re-import), `:204` (B3 clear is gated on `$wasNew`),
`:212` (dispatch skipped when `ACTION_FLAGGED_CONDITION`).

**Scenario:** an existing, not-yet-ignored product is re-imported via `POST /api/product-import`
with `condition: 'refurbished'`. Line 134 writes `pending_ai`; `ListingHealthService::apply()`
(`:197`) flips `is_ignored = true` and returns `ACTION_FLAGGED_CONDITION`; line 204 does nothing
because `$wasNew === false`; line 212 skips the dispatch. Result: `status = 'pending_ai'`,
`is_ignored = true`, no job — identical to the 28 rows the migration is about to clear, and the
migration is one-shot. The builder found this, documented it in `docs/questions.md:9`, and pinned
the stuck behaviour with `ProductImportControllerTest::an_existing_products_status_is_not_cleared_by_the_brand_new_only_b3_guard`.

**Why the spec's scoping rationale does not hold at this site:** the spec left existing products
alone because "a job may be in flight". At this line the `pending_ai` was written by *this same
request* at `:134`, so the comment at `:201-203` ("keeps whatever status it already had") is
factually wrong. And an in-flight `ProcessPendingProduct`, if one exists, tolerates a non-pending
status (`ProcessPendingProduct.php:49-54` warns and continues) and then writes `status = null`
itself (`:81`, `:153`, `:182`) — so clearing here can never strand a job, while not clearing
strands the row forever whenever no job is in flight. Clearing is strictly safer in both cases.

**Exposure:** low. The extension no longer calls `/api/product-import` (`chrome_extension/background.js:5-7`
— the walker's payload "no longer matched the server's validation"; the rescan walk POSTs only to
`ingest-offer`, `:134`). This is a legacy/manual endpoint, hence MEDIUM not HIGH.

**Fix (one token + comment + flip the pinning test):** at `:204` drop the `$wasNew &&` guard, or —
cleaner — do not put `'status' => 'pending_ai'` into `$productUpdates` at `:134` when the outcome
will not be dispatched (requires moving the `apply()` call above the product update, which is a
larger reorder; the one-token change is fine). Rewrite the `:199-203` comment to say the status was
just set at `:134`. Invert the assertion in the pinning test to `status => null`. Acceptable to
defer to the next pass if the owner prefers to keep this deploy spec-exact, but it should not be
left with the misleading comment.

## LOW

### L1 — `AiUsageService::record()`'s two `Log::` calls sit outside its own guards

**Where:** `app/Services/AiUsageService.php:66` (`Log::warning`, unguarded) and `:86`
(`Log::error`, inside a `catch` block, not itself guarded).

**Scenario:** the log channel write throws — Monolog's `StreamHandler` raises
`UnexpectedValueException` when `storage/logs` is unwritable; Laravel's `LogManager` only falls
back to the emergency logger when the *driver cannot be built*, and Laravel sets no
`exceptionHandler` on the Monolog logger, so a handler write failure propagates out of
`Log::error()` → out of `record()` → out of `GeminiService::generate()` after a successful,
billed HTTP call. The class docblock (`:37`) and the spec both promise "never throws".

**Why LOW:** systemic — every other `Log::info` in the job would throw under the same condition,
so this is not a new failure mode for the pipeline. But the guarantee is the whole point of this
class and the fix is trivial.

**Fix:** wrap the whole body of `record()` in an outer `try { … } catch (\Throwable) { /* accounting must never break the AI call */ }`
(or `rescue(fn () => …, report: false)`), keeping the inner `Log::error` so the diagnostic line is
still attempted.

### L2 — `$warnedModels` dedupe collapses to once-per-job on the worker

**Where:** `app/Services/AiUsageService.php:34` (`private array $warnedModels`), no container
binding for `AiUsageService`/`GeminiService`/`AiService` anywhere in `app/Providers` (grep
returned nothing), and both jobs call `app(AiService::class)` per `handle()`
(`ProcessPendingProduct.php:73`, `RescanProductFeatures.php:81`).

**Scenario:** each job gets a fresh `AiService → GeminiService → AiUsageService` graph, so the
"once per instance" guard fires once per job. An unpriced model on a 600-product import emits
~600 warnings — the flood B2 was meant to prevent. Moot today (B2 priced both prod models), but
the next `.env` model swap without a pricing entry re-creates it.

**Fix:** `$this->app->singleton(AiUsageService::class)` in `AppServiceProvider::register()` —
queue workers are long-lived processes, so the dedupe then holds for the worker's lifetime.
Container-resolved `GeminiService` will receive the shared instance (the `new AiUsageService()`
constructor default only applies to manual `new GeminiService()`); the existing per-instance test
(`AiUsageServiceTest::a_new_service_instance_warns_again_for_a_previously_warned_model`) still
passes because it uses `new`. Alternatively `Cache::add("ai-usage:unpriced:{$model}", 1, 3600)`
for cross-process dedupe.

## NIT

### N1 — `usageMetadata` reaches `record(array …)` without an `is_array()` guard under `strict_types`
`app/Services/GeminiService.php:99`: `$result['usageMetadata'] ?? []`. If Gemini ever returned a
scalar here, `GeminiService` has `declare(strict_types=1)`, so the `array $usageMetadata` boundary
would `TypeError` *before* `record()`'s guards — the same class of escape A2 just closed for
`$model`. Gemini's schema makes this practically unreachable; `is_array($result['usageMetadata'] ?? null) ? … : []`
closes it for free.

### N2 — new `$tenantId` parameters on `evaluateProduct()` / `rescanFeatures()` are undocumented
`app/Services/AiService.php:36`, `:112`. `generate()` got a full `@param` (`GeminiService.php:29-32`);
the two domain methods did not. The parameter's meaning ("pass the product's tenant when calling
from a queued job, where tenancy is never initialized; request-context callers may omit it") is
not obvious from `?string $tenantId = null` and is exactly the thing the next builder will get
wrong. One `@param` line each.

### N3 — `declare(strict_types=1)` absent from three touched files (pre-existing)
`app/Jobs/ProcessPendingProduct.php`, `app/Jobs/RescanProductFeatures.php`,
`app/Http/Controllers/Api/BatchImportController.php`. Not introduced by this change. Do not add
it blindly in this pass: `evaluateProduct(?float $scrapedPrice …)` receives `$product->best_price`
from the job, and enabling strict mode there changes coercion at that boundary — verify the
accessor's return type first.

### N4 — five other `AiService` methods hold a tenant model and could forward `tenant_id`
`sweepCategoryPollution(Category …)`, `assignCategories(Collection …)`, `generatePresetContent(Preset …)`,
`generateCompareContent(Category …)`, `generateLandingPageContent(Category …)`. All current callers
initialize tenancy (verified: `AiSweepCategory.php:33`, `AiAssignCategories.php:30`,
`GenerateCompareContent.php:38`, `GenerateLandingPage.php:43`, `GeneratePresetContent.php:40`),
so the fallback is correct today and the spec scoped these out. Forwarding `$category->tenant_id`
costs one argument each and would make attribution survive a future move of any of them to a
queued job. Defense-in-depth only.
