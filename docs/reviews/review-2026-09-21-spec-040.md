### S1 — Refactor safety rests on zero executed evidence; HEAD diff still owed
`app/Services/Seo/GoogleAnalyticsService.php:79-100, 176-215`

- What I could confirm: in the current code the index/fallback-key mapping is correct against the request's declared metric order — `0 sessions / 1 totalUsers→users / 2 engagedSessions→engaged_sessions / 3 keyEvents→conversions / 4 bounceRate→bounce_rate`, dimension index 0 — and those output keys map to the right `ga4_*` columns in the action. The fallback key names also match the tracked, unmodified fixture `tests/Fixtures/Seo/ga4-sample-response.json`. There is no off-by-one in what ships. Casts are equivalent for real GA4 values (`(int)(float)"310"`; bounce rate stays float).
- What I could not confirm: byte-identity with HEAD (old default values, any rounding/trim in the old inline code).
- Why it matters more than usual: **no test executes this parsing at all.** There is no `GoogleAnalyticsServiceTest`; every GA4 fake overrides `fetchLandingPageMetrics()` / `fetchOutboundClicks()` wholesale; the fixture is referenced by no test. And the "array fallback" branch cannot be reached through the documented seam, because `makeClient()` must return `BetaAnalyticsDataClient`, which is `final` (`vendor/google/analytics-data/src/V1beta/Client/BetaAnalyticsDataClient.php:91`). So "837 passed" says nothing about this refactor, and the array-fallback branches (now including a new `'clicks'` key) are unreachable code.
- Failure scenario: a slip in the extraction would first surface as wrong numbers in prod; a slip in the click parsing would surface as silent zeros (see N7).
- Fix: (a) someone with git runs `git diff HEAD -- app/Services/Seo/GoogleAnalyticsService.php` and checks the four things above — one minute. (b) Pull the duplicated `makeClient() → runReport() → close()` trio (lines 55/74-75 and 127/149-150) into one `protected function runReport(RunReportRequest $request): iterable`; tester overrides that to return real `Row`/`DimensionValue`/`MetricValue` objects and asserts both methods' output. That gives real-shape coverage, removes the duplication, lets `close()` move into a `finally` (it is skipped today when `runReport()` throws — a 35-day backfill with a failing click call leaks 35 clients), and lets the dead array-fallback branches be deleted.

### S2 — Backfill window in the spec (35 days) makes the new widget delta wrong for ~3 weeks
`docs/specs/040-ga4-outbound-clicks.md:59,109` with `app/Filament/Widgets/Seo/KpiCardsWidget.php:35-36,107-109`

- Widget "prior 28d" = `today-55 … today-28`. A 35-day backfill anchored on yesterday covers `today-35 … today-1`, i.e. only 8 of the prior window's 28 days. The other 20 days hold the column default `0`, which is indistinguishable from "no clicks" (consequence of NOT NULL default 0).
- Failure scenario: current 28d = 5, prior (8 real days) = 1 → card shows "+400% vs prior 28d" in green. Certain, not hypothetical, on c2d.
- Fix: no code. Owner step becomes `pw2d:seo:pull {tenant} --ga4-window-days=56`. Update the spec's Backfill and Tasks lines.

### S3 — Each date is read exactly once, at 03:00 UTC the next morning; late-processed clicks are never counted
`routes/console.php:15` (no window flag) with `app/Console/Commands/Seo/PullSeoMetricsCommand.php:30` (`--ga4-window-days=1`)

- Outside this diff, but it decides whether the new number is right. Verified: nightly GA4 window is 1 day; verified: upsert is replace-not-increment and a failed click fetch no longer zeroes history, so re-pulling is safe. Not verifiable from here: how complete GA4 is for day D at 03:00 UTC on D+1 (Google documents up to 24-48h for full processing; property timezone also shifts the day boundary — flagged for sessions in the phase-2a review, item 5). GSC already gets a 4-day window for the same reason (F19).
- Failure scenario: a store click at 22:00 on D not yet processed at 03:00 → stored 0 for D, never revisited. At ~6 clicks per 28 days, one lost event is a ~17% error in the headline metric.
- Fix: `Schedule::command('pw2d:seo:pull --ga4-window-days=3')`. Cost: 12 GA4 calls/night across both tenants. Empirical check if the owner wants proof first: a week after deploy, re-pull D-7…D-3 and see whether any stored count changes.

### S4 — `limit` 500 with no pagination and no `order_bys`: once landing rows exceed 500, the click-only path overwrites real session data with zeros
`app/Services/Seo/GoogleAnalyticsService.php:71` (truncation is pre-existing) with `app/Actions/Seo/PullGa4Metrics.php:96-111` (new)

- Click report: clean — 500 distinct clicked pages in one day is orders of magnitude away.
- Landing report: 100-300 rows/day today against a hard cap of 500 (the API default would be 10,000; `chunk_size` is a page size used here as a cap). Headroom is 1.7-5x; a growth step or one JS-executing crawler day crosses it. At HEAD that was a silent undercount. New: a clicked page whose landing row fell past row 500 is treated as "not a landing page" and gets a zeroed-session batch row; on any re-pull (backfill today, every night if S3 is adopted) that row overwrites previously stored real sessions/users/bounce with 0, because row order is unspecified and differs between calls.
- Fix (minimal): `Log::warning` when `$rows->count() >= $limit` so truncation is visible the first day it happens. Fix (root cause, cheap once S1's `runReport()` seam exists): offset loop like `GoogleSearchConsoleService.php:93-107`.

## NIT

- **N1 — history narrative in a docblock.** `GoogleAnalyticsService.php:110-118`: "despite this method's first draft claiming otherwise… prod has 0 of 1,959 rows" is changelog plus a number that rots. Keep the invariant only: `pagePath` and `landingPage` are both path-only, so `url`/`url_hash` match across the two methods. Class docblock (`:20`) and `PullGa4Metrics` docblock (`:14`) still describe landing-page metrics only.
- **N2 — comment says something untrue.** `PullGa4Metrics.php:141-142`: "Fresh inserts still get the column's DB default (0)". They get the batch's explicit seeded `0`; the DB default is never involved. Behaviour is right, wording is not.
- **N3 — model docblock now false.** `SeoMetric.php:14-15` "the other group remains null": `ga4_outbound_clicks` is `0` on every `gsc` row. `docs/database-schema.md:80` gets this right.
- **N4 — duplicated 13-key row literal.** `PullGa4Metrics.php:60-74` vs `97-111`. Key sets are identical today (checked). `upsert()` derives its column list from the first row, so a future column added to one literal only gives a bindings-count SQL error or misaligned values. A small private row builder removes the hazard. Related: fetch into `$clicksByUrl = …->pluck('clicks','url')->all()` inside the try and merge after it — `null` replaces the boolean flag and a throw mid-loop can no longer leave a half-merged batch (theoretical today: the service always returns well-formed rows).
- **N5 — log redaction parity.** `PullGa4Metrics.php:116-120` logs raw `$e->getMessage()`; the outer path redacts the service-account path via `PullResult::fromThrowable()`. Realistically unreachable (a credentials error would already have thrown in the landing call a moment earlier) and it mirrors `PullGscMetrics.php:100-103`. Context (tenant, date) is useful; no secrets.
- **N6 — `(not set)` / empty `pagePath`.** No filter; such a click merges into the same-named landing row or creates one. I would keep it that way: dropping it would undercount the tenant total. Only indirect way click-derived data can fail the landing pull: a `pagePath` over 500 chars fails the single upsert under MySQL strict mode. Same exposure already exists for `landingPage`; optional skip-and-log on `mb_strlen($url) > 500`.
- **N7 — a permanently broken click query looks exactly like "no clicks".** Log-only by spec, and 0 is the normal value. Acceptance check after the backfill: per-tenant 28-day sums must equal the probe (c2d 5, pw2d 1); if 0, grep the log for `outbound clicks failed`. Worth adding that grep to the weekly procedure.
- **N8 — widget null-delta styling.** `KpiCardsWidget.php:151-152`: prior = 0 renders "No comparison data" with a down arrow in `danger`. Copied from the five neighbours, but for store clicks it is the default state (pw2d: 1 click / 28d). Sixth copy of the same block; a private `deltaStat()` helper would fix styling and duplication together.
- **N9 — stale click-only rows.** Successful re-pull where a formerly click-only URL is absent from both responses: row is not in the batch, stored count survives. Asymmetric with the landing-row case but identical to how vanished landing rows already behave. Accept.
