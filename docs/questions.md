# Questions / Findings from Test Engineering

## Spec 030 (landing-page freshness engine) — builder judgment calls (2026-08-10)

Spec 030 left a few implementation details to the builder. Logged here per CLAUDE.md
("if the spec is unclear, write to docs/questions.md" — none of these blocked the
build, but they're worth the owner/architect's eyes):

1. **No pre-existing `ProductObserver`.** The spec says "find the existing Product
   observer (app/Observers/)" — no such file existed (only `CategoryObserver` and
   `FeatureObserver` were registered). Created `app/Observers/ProductObserver.php`
   following the same pattern and registered it in `AppServiceProvider::boot()`.

2. **`AuditLandingPagesCommand` location.** Put alongside `GenerateLandingPage.php`
   directly under `app/Console/Commands/` (not a `LandingPages/` subfolder) since
   that's where its sibling command already lives — mirrors that convention rather
   than the `app/Console/Commands/Seo/` subfolder pattern used for GSC/GA4 commands.

3. **`pick_ineligible` vs `render_short` overlap is structural, not a test gap.**
   `LandingPageController`'s render-time filter (is_ignored=false, status=null,
   category_id not null) is a strict SUBSET of `SelectLandingPagePicks`' eligibility
   filter. Any product that fails render also fails re-selection, so `render_short`
   almost always co-occurs with `selection_drift`, and often `pick_ineligible` too
   (which explicitly checks is_ignored/detached/deleted). The one exception is
   `status` (e.g. `pending_ai`) — `pick_ineligible`'s contract per the spec text
   doesn't list it, so a status-only change fires `render_short`+`selection_drift`
   WITHOUT `pick_ineligible`. Tests document this via `assertContains` rather than
   exact-array assertions where the overlap is unavoidable; one test
   (`render_short_fires_distinctly_from_pick_ineligible_when_a_pick_goes_pending`)
   pins down the one case where they diverge.

4. **`price_drift` skip rule for a zero/negative snapshot.** The spec says "picks
   without snapshots are skipped" — treated a stored `est_price_snapshot` of `0` the
   same as `null` (skip, avoid a divide-by-zero) since `0` is not a realistic priced
   product and would otherwise produce a nonsensical (infinite) deviation.

5. **Filament `TernaryFilter` for freshness.** Not explicitly requested by the spec
   (only the badge column + nav badge + default sort were), but added a "Stale
   only / Fresh only" table filter since it's a natural companion to the badge
   column and cheap to add. Flag if this is unwanted scope creep.

## Finding: `Product.ai_summary` can itself contain a fabricated listing-condition claim (leaks into schema + any downstream AI prompt that includes it)

**Discovered:** 2026-08-01, while verifying the Spec 027 landing-page GROUNDING fix (owner caught the AI inventing "renewed" for the Logitech G915 TKL pick, which retails higher than our scraped price).

**Root cause, precisely located:** Product #2723 (Logitech G915 TKL White Tactile, pw2d tenant)'s stored `ai_summary` — generated by `AiService::evaluateProduct()` (the AI Bouncer, a completely different pipeline stage than the landing-page generator) — literally contains the sentence "This is a premium gaming keyboard, **even if renewed**, offering top-tier wireless performance...". Our scraped data (`ProductOffer.raw_title` / `scraped_price`) has no condition field and no "renewed"/"refurbished" wording anywhere — `evaluateProduct()`'s own prompt fabricated the condition from world knowledge (retail price of a new G915 TKL vs. our scraped price), at ingestion time, independent of anything Spec 027 does.

**Where this leaks today:**
1. `SeoSchema::buildListItem()` renders `strip_tags($product->ai_summary)` verbatim into the ItemList JSON-LD `description` field on every page that lists this product (compare page, and the `/best/mechanical-gaming-keyboards` landing page) — confirmed live: `curl` of the regenerated landing page still shows `"even if renewed"` in its ItemList schema, sourced from this product's `ai_summary`, NOT from the landing-page AI call.
2. `AiService::generateLandingPageContent()`'s prompt includes each pick's `ai_summary` as context (`Summary: {$summary}` in the per-pick data line) — so the fabricated "renewed" claim was almost certainly the proximate source the landing-page model copied/paraphrased from in the first (pre-GROUNDING-fix) regeneration, not pure independent hallucination.

**Verified the GROUNDING fix (this session) works despite the polluted input:** even with `ai_summary` still containing "even if renewed" in the prompt payload, the regenerated pick #1 body after the GROUNDING clause was added makes **zero** mention of condition — the explicit "the payload does not include listing condition — say nothing about it, ever, regardless of what other context implies" instruction successfully overrode the misleading `ai_summary` text for landing-page prose specifically. That fix is confirmed working; this finding is about the underlying `ai_summary` data (and the `evaluateProduct()` prompt that produced it) being independently polluted and rendering elsewhere.

**Recommendation (not actioned — out of scope for the Spec 027 prompt task I was given, and would need a separate AI Bouncer re-scan pass, which has cost/scope implications beyond this session):**
- Add a condition-fabrication guardrail to `AiService::evaluateProduct()`'s prompt (STAGE 3 scoring rules) similar to the GROUNDING clause just added to `generateLandingPageContent()` — the failure mode is identical (price looks surprising relative to world-knowledge retail price → model invents a condition explanation).
- Consider a one-time audit/re-scan (`pw2d:ai-sweep`-style command, or a manual grep) for `ai_summary` fields containing condition words (renewed/refurbished/used/open-box) across existing products, since this is unlikely to be isolated to one product.
- Until fixed at the source, `SeoSchema::buildListItem()`'s schema `description` field (and any future prompt that includes `ai_summary` as context, as `generateLandingPageContent()` now does) inherits whatever `evaluateProduct()` fabricated.

## Bug: BatchImportController uses MySQL-only SUBSTRING_INDEX

**File:** `app/Http/Controllers/Api/BatchImportController.php` (line 43)

**Issue:** The duplicate-ASIN detection query uses `SUBSTRING_INDEX(SUBSTRING_INDEX(url, '/dp/', -1), '?', 1)`, which is a MySQL-specific SQL function. This works correctly in production (MySQL) but will throw `SQLSTATE[HY000]: General error: 1 no such function: SUBSTRING_INDEX` in any SQLite environment (local dev with non-MySQL DB, CI/CD test databases).

The function is not available in SQLite, PostgreSQL, or other common development databases. This also means 7 of the BatchImportController tests are automatically skipped on SQLite and only run on MySQL.

**Recommendation:** Replace the `SUBSTRING_INDEX` approach with PHP-level ASIN extraction after a simpler `LIKE '%/dp/%'` query, or use a stored URL format that makes the ASIN directly queryable (e.g. store the ASIN as a separate column on `product_offers`).

## Note: Tenant model GeneratesIds incompatibility with string PKs in SQLite

**File:** `vendor/stancl/tenancy/src/Database/Concerns/GeneratesIds.php`

**Issue:** Because `config('tenancy.id_generator')` is `null`, `GeneratesIds::getIncrementing()` returns `true`. This causes Eloquent to call `lastInsertId()` after any `Tenant::create()` call and overwrite the string PK (e.g. `'best-mics'`) with the integer SQLite rowid (`1`). The result is that `$tenant->id` after creation equals `1`, not `'best-mics'`.

This affects any test that calls `tenancy()->initialize($tenant)` after `Tenant::create()` — `tenant()->getTenantKey()` returns `1`, not `'best-mics'`, causing FK violations when BelongsToTenant models are created.

**Workaround used in tests:** Use `app()->instance(TenantContract::class, $mock)` with a mock tenant object (same technique as `TenantCacheKeyTest`) instead of calling `tenancy()->initialize()` directly.

**Note:** This does not affect production (MySQL uses string PKs without auto-increment interference) or existing HTTP-level tests (where tenant ID lookup goes through the DB, not through the in-memory model).

## Builder decisions on Spec 027 ("Best X" landing pages, T1) not fully covered by the spec

**File:** `app/Actions/SelectLandingPagePicks.php`, `app/Console/Commands/GenerateLandingPage.php`, `app/Livewire/ProductCompare.php`, `app/Support/SeoSchema.php`

Spec 027 §4 defines `picks[].role ∈ overall/budget/premium/preset:{slug}` as an apparently exhaustive enum, but §4's own "fill remaining slots (to N=7) with next-highest overall scores" step doesn't say what role those fill-in entries get. Rather than invent a 5th role value not in the documented enum (which the frontend/tester agents build against literally), fill-in picks reuse role `overall` — they're simply lower ranks within the same default-weighted "overall" ordering as the #1 pick. If a distinct visual treatment for fill-in vs. the #1 badge is wanted, the frontend should key off *position*, not a unique role string.

Spec 027 §4's "Best for {preset}" scoring says "top-scored under that preset's weights" without specifying the exact algorithm. `ProductCompare`'s default-weight scoring path (`ProductScoringService::scoreAllProducts`, explicitly mandated for "Best Overall") normalizes scores per-feature and defaults *unlisted* features to a neutral weight of 50 — but there's no established "apply this preset's weights and re-rank" code path anywhere in the live app (the preset URL param only changes SEO copy on the compare page, not the product order). The only existing precedent for "preset-weighted product ranking" is `AiService::generatePresetContent()`'s approach: sum of `(feature raw_value × pivot weight)` over only the preset's explicitly-weighted features (unlisted features contribute nothing). `SelectLandingPagePicks` mirrors that established pattern for preset picks, rather than inventing a second scoring algorithm.

`GenerateLandingPage`'s guard when a page already exists without `--regenerate` returns `self::SUCCESS` (a SKIP, not a failure) — mirrors `GenerateCompareContent`'s existing-content skip convention. On `--regenerate` without `--publish`, an existing page keeps its current `status` (a live published page is never silently unpublished by a content refresh, and a draft is never silently auto-published).

Spec 027 §7 lists "Compare page → landing page: one contextual link in `compare-content.blade.php`" under Task §11 as a **T2 (frontend)** deliverable, and the T2 agent built that partial defensively guarded on an `$landingPage` variable ("before the backend wires the variable in"). Since the partial is dead without a supplier, T1 wired it: added `ProductCompare::publishedLandingPage()` (a `#[Computed]` lookup by `category_id` + `status='published'`) and passed it into the `compare-content` include. Flagging this here since it's outside T1's literal task list but the alternative was shipping unreachable frontend code.

The `image + ai_summary present` pick-eligibility gate (§4) is implemented against `Product::image_url` (the existing computed accessor: local `image_path` → best offer image → any offer image) rather than a raw `image_path IS NOT NULL` check — more inclusive, and matches what the site actually renders as "having an image" everywhere else.

## Builder decisions on Spec 029 (Extension Rescan v2, Phase A — server) not fully covered by the spec

**Files:** migrations, `app/Support/ListingHealth.php`, `app/Services/ListingHealthService.php`, `app/Services/PriceTierRecalculator.php`, `app/Jobs/RecalculateCategoryPriceTiers.php`, `app/Services/OfferIngestionService.php`, `app/Http/Controllers/Api/{OfferIngestionController,BatchImportController,ProductImportController}.php`, `app/Actions/SelectLandingPagePicks.php`, `app/Console/Commands/RecalculatePriceTiers.php`.

**`products.amazon_reviews_count` nullability (extra migration, not in the spec's migration list).** Spec 029 only lists the `product_offers` migration (`condition`/`listing_flags`/`health_checked_at`). Storing `null` for a missing reviews_count (A1's explicit requirement) is impossible on the existing `unsignedInteger('amazon_reviews_count')->default(0)` column — it's `NOT NULL` at the DB level. Added a second migration (`2026_08_10_000002_make_amazon_reviews_count_nullable_on_products_table.php`) making the column nullable. `->change()` works without `doctrine/dbal` on Laravel 12 (already used elsewhere in this codebase, e.g. `2026_02_15_120228_increase_affiliate_url_length.php`).

**reviews_count refresh semantics widened from "backfill-only" to "always refresh to the latest reported value."** The pre-existing code only wrote `amazon_reviews_count` when the STORED value was empty (`!empty($product->amazon_reviews_count)` guard) — a one-time backfill, not a refresh. A1 says "update the product's amazon_reviews_count when provided" without qualifying "only if currently empty," and F38's whole premise is that refresh should heal/freshen stored data, not just fill gaps once. Changed all four ingestion paths (OfferIngestionService's existingOffer + matched branches, BatchImportController's refresh branch, ProductImportController's refresh branch) to: `reviews_count` provided (non-null) → always overwrite with the latest value; omitted → leave the stored value untouched (never null it out — that would destroy known-good data, which is different from the CREATE-path "null means unknown" case). `amazon_rating` was deliberately left with its EXISTING semantics unchanged in every path (not called out by the task) to avoid unrequested scope creep.

**Freshly-flagged-condition products don't get an AI evaluation dispatched.** In all three ingestion paths, when `ListingHealthService::apply()` returns `'flagged_condition'` (product just got `is_ignored = true`), `ProcessPendingProduct::dispatch()` is skipped. This extends the pre-existing "a condition-marked title never gets AI-evaluated" convention (`skipped_condition` via `ProductConditionGuard`) to the new DOM-detected condition path — burning a Gemini call on a product we just decided to ignore seemed like clear scope creep to avoid, but it's a judgment call, not explicit in the spec text.

**`RecalculateCategoryPriceTiers` dispatch conditions.** A4 says "after ingestion updates a price on an existing offer." Interpreted narrowly: dispatched only when an offer that ALREADY EXISTED gets its price touched — i.e. `OfferIngestionService`'s `existingOffer` (URL-match) branch always, its `matched` branch only when a `$priorOffer` for that exact (product_id, store_id) was found before the `updateOrCreate` call (a brand-new offer attached to an existing product isn't "updating a price," it's adding one), `BatchImportController`'s refresh branch (once per request via a `$priceUpdated` flag, not per product), and `ProductImportController`'s `!$wasNew` branch. Brand-new PRODUCT creation never dispatches it — `price_tier` is already computed correctly inline at creation via `$category->priceTierFor(...)`, so a category-wide recalc adds no value there.

**Q13 (RecalculatePriceTiers memory) fixed as part of this build**, not left as a separate follow-up — A4 explicitly required chunking, and the new job reuses the exact same code path as the console command, so fixing the unbounded `->get()` was unavoidable to do this correctly. Extracted `App\Services\PriceTierRecalculator::recalculateForCategory()` (uses `Product::where(...)->chunkById(200, ...)`) — both `products:recalculate-tiers` and `RecalculateCategoryPriceTiers` call it, so the console command's existing per-product progress output still works via an optional `?callable $onUpdate` callback. Marked Q13 done in `docs/tasks/todo.md`.

**Rescan-list auth: 403, not 401.** The task description said "rescan-list auth (401 without token)," but the existing `VerifyExtensionToken` middleware — used identically by every sibling extension endpoint — returns 403 (`{'error': 'Unauthorized.'}`), not 401. Per the task's own instruction to "mirror it exactly," the new endpoint uses the SAME middleware unchanged, so it also returns 403. The test (`RescanListControllerTest::it_returns_403_without_a_valid_extension_token`) asserts the real, existing behavior rather than inventing a divergent 401 response for this one endpoint.

**Rescan-list response envelope.** Wrapped as `{"success": true, "offers": [...]}`, matching every sibling GET endpoint's envelope convention (`{success, asins}` from `existingAsins`, `{success, categories}` from `categories`) rather than returning a bare JSON array as the spec's literal shape example (`[{offer_id, ...}]`) might suggest.

**Recognized `listing_flags` values: strictly `['high_price']` for now.** The spec explicitly says "room to grow (e.g. `unavailable`)" but only defines `high_price` as currently recognized, and the task explicitly requires rejecting unknown flag strings with a 422. Implemented as a single source of truth (`App\Support\ListingHealth::RECOGNIZED_FLAGS`) so adding `unavailable` later is a one-line change plus whatever handling `ListingHealthService::apply()` needs for it (none yet — only `high_price` has defined behavior).

**Landing-page-pick warning fires only on the is_ignored transition, not on every repeat report.** A2 says "when a NEWLY-flagged product ... is a current landing-page pick, log a warning." Read literally: the warning is scoped inside `if (!$product->is_ignored) { ... }` in `ListingHealthService::apply()`, so re-scanning an already-flagged listing (still reports `renewed` on a later rescan) doesn't re-log every time — only the actual first transition into `is_ignored = true` does.

**Q1's exact historical trigger for the prod `Duplicate entry` crash wasn't fully reproduced**, but the fix (`updateOrCreate` keyed on `(product_id, store_id)` replacing every raw `ProductOffer::create()` call across all three ingestion paths) is applied as defense-in-depth exactly as A1 specifies, regardless of the precise race that caused it in prod.

## Builder decisions on the 2026-08-10 consolidated audit fixes (Spec 029/030) not fully covered by the audit reports

**Files:** `app/Services/OfferIngestionService.php`, `app/Http/Controllers/Api/{BatchImportController,ProductImportController}.php`, `app/Filament/Resources/LandingPageResource.php` + `.../Pages/EditLandingPage.php`, `app/Console/Commands/GenerateLandingPage.php`.

**B2 fix: the condition-marker skip was moved to right after the existing-offer/AI-match determination (before AI matching itself), not literally at "the create-new step."** All three audit reports describe the fix in terms of the OUTCOME ("existing offer or explicit condition → run normal refresh; otherwise skip"), not the exact line position. Placing the marker-guard check immediately after `existingOffer` is confirmed null — but BEFORE the `AiService::matchProduct()` call — preserves the guard's original efficiency intent (never spend an AI-match call, itself a real cost, on a listing about to be discarded as junk) while still fully closing the B2 bug (a rescan of an EXISTING offer always heals now, regardless of marker). One side effect: for a **brand-new, marker-titled listing that would have matched an existing product via AI** (a title marker appearing on a first-seen offer row for an otherwise-known product, attached via a different store/URL), the guard now fires and skips before that AI-match attempt is ever made — this exact scenario isn't described in any of the three reports (all examples are same-URL rescans), and skipping here mirrors this guard's pre-Spec-029 behavior (it always ran before ANY matching, at the very top of the method) for anything but the same-URL-rescan case B2 targets. If future data shows this edge case matters (a marker title that should have healed via AI-match instead of being dropped), the fix is to move the guard after the AI-match block instead — noted here rather than silently decided.

**The same guard-conditioning logic (`$condition === null && matchesTitle(...)`) was applied to all three ingestion paths' create-new branches, not just where explicitly shown in the reports' code snippets.** The reports' own suggested fix text for B2 says "(or a non-null condition was supplied)" as a bypass condition without spelling out every call site — applied consistently so an explicit, DOM-verified `condition` payload always overrides the marker heuristic even for a genuinely new listing (create it flagged, don't silently drop it).

**`GenerateLandingPage`'s `product_name` persisted-at-generation field is additive to the picks JSON shape**, not documented in Spec 027/030's `picks[].{product_id,role,headline,body}` (+ 030's `est_price_snapshot`) shape. Consumers that iterate picks by explicit key list (`AuditLandingPageFreshness`, `LandingPageController::buildViewModel()`) are unaffected by an extra key; `LandingPage`'s class docblock listing the picks shape was intentionally left as-is (not exhaustively updated) since it already predates `est_price_snapshot`'s addition without being corrected then either — flagging here instead of silently drifting the doc further.

**`EditLandingPage::mutateFormDataBeforeSave()` restores stored pick fields by ARRAY INDEX POSITION**, not by matching `product_id`. This is safe only because the picks Repeater is `addable(false)/deletable(false)/reorderable(false)` (already enforced pre-audit) — index alignment between the stored record and the submitted form data is guaranteed. If a future change ever allows reordering/adding/removing picks in Filament, this restoration logic would need to key off something stable (e.g. a hidden dehydrated pick UUID) instead of array position.

## Builder judgment calls — Spec 029 Phase B (extension), 2026-08-10

**Files:** `chrome_extension/{manifest.json,popup.html,popup.js,content.js,background.js}`.

**"High price" flag fires on exact leaf text scoped to the buy-box column, without requiring the "Learn more" disclosure to be found in the DOM.** The spec describes the label as "adjacent to a Learn more disclosure"; the implemented predicate is: a leaf element (`span/h1–h6/div` with no child elements) whose entire trimmed text is exactly `High price`, searched only inside `#rightCol / #desktop_buybox / #buybox / #apex_desktop`. Requiring the "Learn more" text too was rejected because Amazon frequently renders disclosures inside popover/ajax containers that aren't in the initial DOM — the exact-text + region scoping already excludes review/description false positives. If false positives appear in practice, tighten by adding the ancestor "Learn more" check inside `detectListingHealth()` (single function, one place to fix).

**Rescan payload sends the DB-stored offer URL, not the tab's final URL.** `OfferIngestionService` matches the existing offer by exact `url`; Amazon redirects `/dp/ASIN` to slugged canonical URLs, so posting `tab.url` would miss the match and create duplicate offers. The worker walks `offer.url` from rescan-list and posts that same string back.

**Rescan `updated` counter includes server actions `refreshed|matched|created`.** For a work-list built from existing offers the action is essentially always `refreshed`; `matched`/`created` can only occur if the offer row was deleted mid-run — counted as updated rather than inventing a separate bucket.

**Unavailable listings are counted `skipped`, not refreshed.** `extractProductPageData()` early-returns `{unavailable:true}` before extracting a title, and `raw_title` is required by the ingest contract, so there is nothing trustworthy to POST. Consequence: a listing that went permanently unavailable keeps its stale data + old `health_checked_at`, so it keeps sorting first in future rescan lists. Proper handling is the spec's own future `unavailable` listing-flag (ListingHealth "room to grow") — deliberately not invented client-side now because the server wouldn't accept the flag (422 on unknown flags).

**SERP concatenated-title dedup was kept (B4 "untouched raw title").** `extractSerpProducts()` still collapses Amazon's DOM artifact where the hidden `.a-truncate-full` copy concatenates with the truncated copy ("Title…Title…"). That repair reconstructs the actual on-page title rather than cleaning it; removing it would ship garbage titles no human ever saw. No trimming/cleaning of the real title happens anywhere (`.trim()` of whitespace only). The pre-existing client-side skip of renewed/refurbished SERP cards was REMOVED per B4 — those cards are now sent with an explicit `condition` so the server flags them.

**`extractReviewsCount()` now returns `null` (never 0) and serves both SERP cards and product pages.** The SERP flow is unaffected (its `< 5` gate treats null like 0); the product-page flow previously coerced missing counts to 0, which the server would have stored — that was the B3 bug. Product-page strategies (`#acrCustomerReviewText`, `[data-hook="total-review-count"]`, `#averageCustomerReviews` aria-labels, reviews-anchor text) run before the card strategies because they're ID-anchored and can't false-positive from carousel widgets.

**Single Amazon import (popup → batch-import) now also sends `condition` + `listing_flags`** from `detectListingHealth()`. Not explicitly listed in B1–B4, but the server accepts them on batch-import (A2) and shipping the stronger DOM signal on every path is the spec's intent; omitting it only on the single-import path would leave a blind spot.

**Rescan run state persists to `chrome.storage.local` and restores as PAUSED after a service-worker restart.** MV3 workers can be killed mid-run; auto-resuming headless after a restart risks hammering Amazon unattended, so the user explicitly presses Resume (which retries the in-flight offer — refreshes are idempotent).

**No new manifest permissions.** `chrome.tabs.create/update/remove/sendMessage` and `tabs.onUpdated` need no `tabs` permission; the rescan flow never reads `tab.url`; `storage` was already declared. Version bumped 1.0 → 1.1.

## Builder judgment calls — Spec 029 `unavailable` listing-flag (server + extension), 2026-08-12

**Files:** `app/Support/ListingHealth.php`, `app/Services/ListingHealthService.php`, `app/Services/OfferIngestionService.php`, `app/Http/Controllers/Api/{BatchImportController,ProductImportController}.php`, `app/Actions/{SelectLandingPagePicks,AuditLandingPageFreshness}.php`, `chrome_extension/{manifest.json,content.js,background.js,popup.js}`. Supersedes the "Unavailable listings are counted `skipped`" entry in the 2026-08-10 Phase B section above — that deliberate deferral is now implemented.

**stock_status coercion lives in `ListingHealthService::apply()` via a new optional `$payloadStockStatus` parameter, not in each ingestion path.** The task allowed either home; `apply()` is the one choke point all six flag-handling call sites already route through, so the rule can't drift between paths. The parameter is necessary (rather than reading `$offer->stock_status`) because by apply()-time the offer column already holds the fallback-preserved PREVIOUS value (`$data['stock_status'] ?? $existingOffer->stock_status`) — the service cannot tell "explicitly reported in_stock" from "preserved stale in_stock" without being told what the payload actually carried. Default `null` keeps the signature backward compatible.

**An explicit payload stock_status always beats the coercion.** `unavailable` + explicit `stock_status` is contradictory on Amazon today, but the extension DOM-inspected the live page — if a future layout ever reports both, the explicit observation is the stronger signal. Tested (`an_explicit_payload_stock_status_is_never_overridden_by_the_unavailable_flag`).

**The coercion fires in the negative-condition branch too, but never in the 'unknown' stamp-only branch.** A renewed listing that is also currently unavailable gets both facts stored (condition + flag + out_of_stock). The 'unknown' branch stores neither flags nor stock — flags off an unverified page are untrusted (029B-B3), and a stock write would be trusting the same unverified data.

**`BatchImportController`'s empty-price delisting heuristic now exempts `unavailable`-flagged payloads.** Pre-existing behavior: a refresh with no price → `is_ignored = true` (dead listing). Unavailable pages legitimately send `price: null` (the buy-box has no price), and the popup's single Amazon import routes through batch-import — without the exemption, the owner's own QA flow would have HIDDEN the product instead of flagging the offer, directly contradicting A2's "product stays visible". The two now-reachable direct `$p['price']` accesses in the refresh branch gained `?? null` guards (`priceTierFor()` is already nullable). Not spelled out in the task; without it item 3's semantics were unachievable on this path.

**`PICK_EXCLUDING_FLAGS` is a separate constant from `RECOGNIZED_FLAGS` even though the lists are identical today.** Intersection checks in `SelectLandingPagePicks`/`AuditLandingPageFreshness` read the new constant; a future flag (e.g. something informational) may be worth storing without disqualifying landing-page picks, and conflating the two vocabularies would make that a breaking change instead of a one-line addition.

**Extension: a titled page with a detected `unavailable` flag is reported `condition: 'new'`, never `'unknown'`.** `detectListingHealth()`'s buy-box-loaded check requires purchase-UI elements that unavailable pages may lack; `#availability`/`#outOfStock` were already in that selector list, but the buy-box-column fallback path isn't. An affirmatively detected "Currently unavailable" block on a page with `#productTitle` IS a verified page state — demoting it to 'unknown' would make the server stamp-only, drop the flag, and resurrect the exact endless-rescan loop this change kills. Guarded on `titleEl` so genuinely partial pages still report 'unknown'.

**Extension: price is forced to `null` on unavailable pages even when a fallback strategy found a number.** Strategies 2–3 (centerCol `.a-price`, meta/structured-data) can catch a stale meta tag or carousel price on an unavailable page; none of those is THIS listing's price today, and a phantom price would feed `scraped_price`/tier recalc. `#productTitle`, image, and reviews extract normally.

**The `unavailable` flag fires only on "Currently unavailable" text, not on generic "out of stock".** The task named the "Currently unavailable" availability block (Amazon's canonical dead-listing state). A page whose availability reads "Out of stock" (transient) still gets `stock_status: 'out_of_stock'` from `extractProductPageData()` — same as the pre-change behavior — but no flag; flagging transient stock-outs would churn pick eligibility for listings that recover in days.

## Builder judgment calls + discovered pre-existing bugs — BatchImportController no-price delisting heuristic fix, 2026-08-12

**File:** `app/Http/Controllers/Api/BatchImportController.php` (existing-offer refresh branch), `tests/Feature/BatchImportControllerTest.php`.

**Fix summary:** the dead-listing heuristic (`empty(price) → is_ignored=true, continue`) ran before condition/flag evidence was known, so a no-price RENEWED re-listing (live QA, product 1744/B09Z6PM1PV) got silently delisted with no condition stored and no `health_checked_at` stamp. `$effectiveCondition` is now computed first and the heuristic only fires when `empty(price) && $effectiveCondition` is not in `ListingHealth::NEGATIVE_CONDITIONS` `&& empty($listingFlags)` — any condition or flag evidence now falls through to the normal refresh path so `ListingHealthService::apply()` runs and reports `flagged_condition`.

**"Flagged, not refreshed" — kept the counter as BOTH, matching the established sibling contract.** The task description characterized the fix's outcome as "`flagged` counter incremented (not `refreshed`)". In this controller, `$refreshed++` is unconditional for every existing-offer request that reaches the bottom of the `if ($existing)` branch (early-`continue` heuristic aside) — it is not exclusive with `$flagged`. The pre-existing `b4_an_open_box_title_on_an_existing_offer_rescan_...` test already asserts `['refreshed' => 1, 'flagged' => 1]` for the same "condition evidence on a no-longer-heuristic-blocked refresh" shape. Changing that contract (e.g. suppressing `$refreshed` when `$flagged` fires) would be an unrequested behavior change to the response counters/message wording, so the new regression test asserts `flagged => 1` (the outcome that actually matters — did `ListingHealthService::apply()` run and record the reason) without asserting `refreshed => 0`, consistent with the sibling test's established shape.

**Discovered while verifying against a real local MySQL DB (not sqlite) — 3 pre-existing test failures, unrelated to this fix, left untouched (out of scope):**
1. `duplicate_asin_refreshes_existing_offer_and_does_not_create_new_product` calls `Queue::assertNothingPushed()`, but the controller sets `$priceUpdated = true` unconditionally for every existing-offer refresh (not just when the price actually changed) — `RecalculateCategoryPriceTiers::dispatch()` fires every time, so this assertion fails against a real DB. Reproduced on unmodified `main` (git stash), confirming it predates this change.
2. `high_price_flag_on_a_refreshed_offer_does_not_ignore_the_product` and `unavailable_flag_with_no_price_refreshes_the_offer_and_coerces_stock_without_delisting` both use `assertDatabaseHas('product_offers', ['listing_flags' => json_encode([...])])` against the native MySQL `json` column. Reproduced via raw PDO (bound-parameter and literal `WHERE listing_flags = ?`) outside Laravel entirely: MySQL 9.3 (Homebrew) returns `0` for this direct string comparison even though `CAST(? AS JSON)` on the same value returns `1` — the exact same class of "raw comparison against a `json`-cast column is unreliable on MySQL, sqlite hides it" gotcha already logged in `docs/lessons.md` (2026-08-10), just via `assertDatabaseHas`'s generated `WHERE` clause instead of a raw `LIKE`. Also reproduced on unmodified `main`.

Both are pre-existing, unrelated to the no-price delisting fix, and never previously exercised in this dev environment (these tests only run under `DB_CONNECTION=mysql`, which this project's `phpunit.xml` deliberately overrides to sqlite locally — the "550 passed / 15 skipped" baseline was always a sqlite run). Not fixed here — out of scope for this task, and `assertDatabaseHas`'s behavior on `json` columns depends on the actual production MySQL version/config, which this local Homebrew instance may not match exactly. **My two new regression tests avoid the same trap** by asserting against the model's array-cast accessor (`$offer->fresh()->listing_flags`/`->condition`) instead of `assertDatabaseHas`, matching the already-safe pattern used throughout `OfferIngestionServiceTest`. Recommend a follow-up: audit `assertDatabaseHas` usage against `json`-cast columns repo-wide and either switch to array-cast assertions or `whereJsonContains`-based custom assertions, and re-run the full suite against a real MySQL instance (not just sqlite) periodically to catch this class of bug before prod.
