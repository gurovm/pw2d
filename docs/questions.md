## Builder judgment calls — Spec 031 T1 (`scope=picks` on `GET /api/extension/rescan-list`), 2026-08-16

**Files:** `app/Http/Controllers/Api/OfferIngestionController.php`, `tests/Feature/RescanListControllerTest.php`. No `chrome_extension/` changes (parallel agent owns it — see T2's "Extension UI as built" in `docs/specs/031-content-maintenance-cadence.md`).

**`category_id` under `scope=picks` is ignored entirely, not validated.** The spec left this an open question with a stated owner preference ("ignore it so a stale client param can't narrow the sweep silently") and a caveat ("validate that it isn't a tenant-foreign id if you do accept it"). Implemented as: when `scope=picks`, `category_id` is dropped from the `$request->validate()` rules array entirely — no `Rule::exists`, no type check, nothing. Any value (absent, a real id from an unrelated category, a nonexistent id, a cross-tenant id) is silently accepted and has zero effect on the query. This satisfies the caveat vacuously (a value that is never read can't be used to probe another tenant's category namespace) and matches the stated preference exactly. Verified with a test that supplies both an unrelated real `category_id` and `category_id=999999` (which would 422 under `scope=category`) and confirms both return the identical, full, unfiltered pick set.

**Multi-page pick tie-break: first landing page by `slug` ASC.** `pickProductSlugs()` queries `LandingPage::where('tenant_id', ...)->orderBy('slug')->get(...)` and keeps only the first `landing_page_slug` seen per `product_id` in the reduce (a `Collection::has()` guard). This is deterministic and stable across requests, but the choice of "alphabetically first" itself is arbitrary — no signal in the data (e.g. "most recently published," "role=overall over role=budget") was obviously more correct, and the task explicitly allowed picking "a" deterministic rule rather than requiring a specific one. If a different tie-break is later wanted (e.g. prefer the page where the product's `role` is `overall`), it's a one-line change inside `pickProductSlugs()`'s reduce callback.

**`scope=picks` does not filter by `is_ignored`/`status`, unlike `scope=category`.** Not explicitly spelled out in the spec text, but required for the feature to do its job: the whole point of the weekly picks pass is to catch drift, including a pick that has since gone `is_ignored=true` or drifted into a non-null `status` since the page was last generated/regenerated. Filtering those out would hide exactly the cases Tier 1's "detects, does not authorise a rebuild" response rule exists to surface. Covered by `scope_picks_includes_offers_even_when_the_pick_product_is_ignored_or_pending`.

**The Spec 030 §B1 `LIKE`-vs-PHP-filter regression test cannot be meaningfully expressed on this suite's sqlite connection.** sqlite's TEXT-backed `json()` column preserves Laravel's raw, space-free `json_encode` output, so a hypothetical `picks LIKE '%"product_id":N,%'` implementation of `pickProductSlugs()` would pass every test in `RescanListControllerTest.php` on sqlite — the bug is specific to MySQL's native `json` column re-serializing to a space-padded string on cast to text, which sqlite has no equivalent of. Writing a test that "fails under LIKE" would require either a MySQL-only test run (this suite is sqlite, per `phpunit.xml`) or hand-rolling a fake space-padded fixture, which would prove nothing about the real bug. Mitigation is structural instead, matching `AuditLandingPageFreshnessJob::dispatchForProduct()`'s established pattern: `pickProductSlugs()` never issues a JSON `LIKE` query at all, so the whole bug class is inapplicable by construction — documented in the method's own docblock rather than a false-confidence test.

**Response shape: `landing_page_slug` (and the later `category_id` fix below) are only added to `scope=picks` rows, not `scope=category` rows.** The spec's "Response shape" bullet reads generally ("each row keeps ... and gains landing_page_slug"), but a category-scope rescan isn't about landing pages at all — there's no slug to report, and the extension already knows the `category_id` it asked for. Kept `categoryScopeOffers()`'s row shape byte-for-byte identical to the pre-031 code (verified by the pre-existing category-scope tests passing unchanged).

**Cross-agent finding, fixed same session: `category_id` was missing from `scope=picks` rows.** The parallel T2 (extension) agent's concurrent build of `popup.js`/`background.js` correctly identified — via its own preflight check — that `POST /api/extension/ingest-offer` requires `category_id`, and a picks run spans every category, so each row needs its own `category_id` to complete the ingest round-trip; the T1 task description and spec text as given to me did not call this out. Fixed by eager-loading `product:id,category_id` in `picksScopeOffers()` and mapping `$offer->product?->category_id` into each row (the offer's own product's category — never the ignored request param). +1 regression test asserting two picks in two different categories each report their own product's `category_id`. Full suite re-verified after the fix: 594 passed/19 skipped, no regressions. Logged here since it's a real contract the spec text under-specified, not a builder preference call.

## Finding: `Product.ai_summary` can itself contain a fabricated listing-condition claim (leaks into schema + any downstream AI prompt that includes it)

**Discovered:** 2026-08-01, while verifying the Spec 027 landing-page GROUNDING fix (owner caught the AI inventing "renewed" for the Logitech G915 TKL pick, which retails higher than our scraped price).

**Root cause, precisely located:** Product #2723 (Logitech G915 TKL White Tactile, pw2d tenant)'s stored `ai_summary` — generated by `AiService::evaluateProduct()` (the AI Bouncer, a completely different pipeline stage than the landing-page generator) — literally contains the sentence "This is a premium gaming keyboard, **even if renewed**, offering top-tier wireless performance...". Our scraped data (`ProductOffer.raw_title` / `scraped_price`) has no condition field and no "renewed"/"refurbished" wording anywhere — `evaluateProduct()`'s own prompt fabricated the condition from world knowledge (retail price of a new G915 TKL vs. our scraped price), at ingestion time, independent of anything Spec 027 does.

**Where this leaks today:**
1. `SeoSchema::buildListItem()` renders `strip_tags($product->ai_summary)` verbatim into the ItemList JSON-LD `description` field on every page that lists this product (compare page, and the `/best/mechanical-gaming-keyboards` landing page) — confirmed live: `curl` of the regenerated landing page still shows `"even if renewed"` in its ItemList schema, sourced from this product's `ai_summary`, NOT from the landing-page AI call.
2. `AiService::generateLandingPageContent()`'s prompt includes each pick's `ai_summary` as context (`Summary: {$summary}` in the per-pick data line) — so the fabricated "renewed" claim was almost certainly the proximate source the landing-page model copied/paraphrased from in the first (pre-GROUNDING-fix) regeneration, not pure independent hallucination.

**Verified the GROUNDING fix (this session) works despite the polluted input:** even with `ai_summary` still containing "even if renewed" in the prompt payload, the regenerated pick #1 body after the GROUNDING clause was added makes **zero** mention of condition — the explicit "the payload does not include listing condition — say nothing about it, ever, regardless of what other context implies" instruction successfully overrode the misleading `ai_summary` text for landing-page prose specifically. That fix is confirmed working; this finding is about the underlying `ai_summary` data (and the `evaluateProduct()` prompt that produced it) being independently polluted and rendering elsewhere.

**Recommendation (not actioned — out of scope for the Spec 027 prompt task I was given, and would need a separate AI Bouncer re-scan pass, which has cost/scope implications beyond this session):**
- Add a condition-fabrication guardrail to `AiService::evaluateProduct()`'s prompt (STAGE 3 scoring rules) similar to the GROUNDING clause just added to `generateLandingPageContent()` — the failure mode is identical (price looks surprising relative to world-knowledge retail price → model invents a condition explanation).
- Consider a one-time audit/re-scan (`pw2d:ai-sweep`-style command, or a manual grep) for `ai_summary` fields containing condition words (renewed/refurbished/used/open-box) across existing products, since this is unlikely to be isolated to one product.
- Until fixed at the source, `SeoSchema::buildListItem()`'s schema `description` field (and any future prompt that includes `ai_summary` as context, as `generateLandingPageContent()` now does) inherits whatever `evaluateProduct()` fabricated.

## Bug: BatchImportController uses MySQL-only SUBSTRING_INDEX

**File:** `app/Http/Controllers/Api/BatchImportController.php` (line 43)

**Issue:** The duplicate-ASIN detection query uses `SUBSTRING_INDEX(SUBSTRING_INDEX(url, '/dp/', -1), '?', 1)`, which is a MySQL-specific SQL function. This works correctly in production (MySQL) but will throw `SQLSTATE[HY000]: General error: 1 no such function: SUBSTRING_INDEX` in any SQLite environment (local dev with non-MySQL DB, CI/CD test databases).

The function is not available in SQLite, PostgreSQL, or other common development databases. This also means 7 of the BatchImportController tests are automatically skipped on SQLite and only run on MySQL.

**Recommendation:** Replace the `SUBSTRING_INDEX` approach with PHP-level ASIN extraction after a simpler `LIKE '%/dp/%'` query, or use a stored URL format that makes the ASIN directly queryable (e.g. store the ASIN as a separate column on `product_offers`).

## Note: Tenant model GeneratesIds incompatibility with string PKs in SQLite

**File:** `vendor/stancl/tenancy/src/Database/Concerns/GeneratesIds.php`

**Issue:** Because `config('tenancy.id_generator')` is `null`, `GeneratesIds::getIncrementing()` returns `true`. This causes Eloquent to call `lastInsertId()` after any `Tenant::create()` call and overwrite the string PK (e.g. `'best-mics'`) with the integer SQLite rowid (`1`). The result is that `$tenant->id` after creation equals `1`, not `'best-mics'`.

This affects any test that calls `tenancy()->initialize($tenant)` after `Tenant::create()` — `tenant()->getTenantKey()` returns `1`, not `'best-mics'`, causing FK violations when BelongsToTenant models are created.

**Workaround used in tests:** Use `app()->instance(TenantContract::class, $mock)` with a mock tenant object (same technique as `TenantCacheKeyTest`) instead of calling `tenancy()->initialize()` directly.

**Note:** This does not affect production (MySQL uses string PKs without auto-increment interference) or existing HTTP-level tests (where tenant ID lookup goes through the DB, not through the in-memory model).

## Builder decisions on Spec 029 (Extension Rescan v2, Phase A — server) not fully covered by the spec

**Files:** migrations, `app/Support/ListingHealth.php`, `app/Services/ListingHealthService.php`, `app/Services/PriceTierRecalculator.php`, `app/Jobs/RecalculateCategoryPriceTiers.php`, `app/Services/OfferIngestionService.php`, `app/Http/Controllers/Api/{OfferIngestionController,BatchImportController,ProductImportController}.php`, `app/Actions/SelectLandingPagePicks.php`, `app/Console/Commands/RecalculatePriceTiers.php`.

**`products.amazon_reviews_count` nullability (extra migration, not in the spec's migration list).** Spec 029 only lists the `product_offers` migration (`condition`/`listing_flags`/`health_checked_at`). Storing `null` for a missing reviews_count (A1's explicit requirement) is impossible on the existing `unsignedInteger('amazon_reviews_count')->default(0)` column — it's `NOT NULL` at the DB level. **reviews_count refresh semantics widened from "backfill-only" to "always refresh to the latest reported value."** The pre-existing code only wrote `amazon_reviews_count` when the STORED value was empty (`!empty($product->amazon_reviews_count)` guard) — a one-time backfill, not a refresh. A1 says "update the product's amazon_reviews_count when provided" without qualifying "only if currently empty," and F38's whole premise is that refresh should heal/freshen stored data, not just fill gaps once. This extends the pre-existing "a condition-marked title never gets AI-evaluated" convention (`skipped_condition` via `ProductConditionGuard`) to the new DOM-detected condition path — burning a Gemini call on a product we just decided to ignore seemed like clear scope creep to avoid, but it's a judgment call, not explicit in the spec text.

Interpreted narrowly: dispatched only when an offer that ALREADY EXISTED gets its price touched — i.e. `OfferIngestionService`'s `existingOffer` (URL-match) branch always, its `matched` branch only when a `$priorOffer` for that exact (product_id, store_id) was found before the `updateOrCreate` call (a brand-new offer attached to an existing product isn't "updating a price," it's adding one), `BatchImportController`'s refresh branch (once per request via a `$priceUpdated` flag, not per product), and `ProductImportController`'s `!$wasNew` branch. **Q13 (RecalculatePriceTiers memory) fixed as part of this build**, not left as a separate follow-up — A4 explicitly required chunking, and the new job reuses the exact same code path as the console command, so fixing the unbounded `->get()` was unavoidable to do this correctly. ## Builder decisions on the 2026-08-10 consolidated audit fixes (Spec 029/030) not fully covered by the audit reports

**Files:** `app/Services/OfferIngestionService.php`, `app/Http/Controllers/Api/{BatchImportController,ProductImportController}.php`, `app/Filament/Resources/LandingPageResource.php` + `.../Pages/EditLandingPage.php`, `app/Console/Commands/GenerateLandingPage.php`.

Placing the marker-guard check immediately after `existingOffer` is confirmed null — but BEFORE the `AiService::matchProduct()` call — preserves the guard's original efficiency intent (never spend an AI-match call, itself a real cost, on a listing about to be discarded as junk) while still fully closing the B2 bug (a rescan of an EXISTING offer always heals now, regardless of marker). **The same guard-conditioning logic (`$condition === null && matchesTitle(...)`) was applied to all three ingestion paths' create-new branches, not just where explicitly shown in the reports' code snippets.** The reports' own suggested fix text for B2 says "(or a non-null condition was supplied)" as a bypass condition without spelling out every call site — applied consistently so an explicit, DOM-verified `condition` payload always overrides the marker heuristic even for a genuinely new listing (create it flagged, don't silently drop it).

This is safe only because the picks Repeater is `addable(false)/deletable(false)/reorderable(false)` (already enforced pre-audit) — index alignment between the stored record and the submitted form data is guaranteed. ## Builder judgment calls — Spec 029 Phase B (extension), 2026-08-10

**Files:** `chrome_extension/{manifest.json,popup.html,popup.js,content.js,background.js}`.

**"High price" flag fires on exact leaf text scoped to the buy-box column, without requiring the "Learn more" disclosure to be found in the DOM.** The spec describes the label as "adjacent to a Learn more disclosure"; the implemented predicate is: a leaf element (`span/h1–h6/div` with no child elements) whose entire trimmed text is exactly `High price`, searched only inside `#rightCol / #desktop_buybox / #buybox / #apex_desktop`. Requiring the "Learn more" text too was rejected because Amazon frequently renders disclosures inside popover/ajax containers that aren't in the initial DOM — the exact-text + region scoping already excludes review/description false positives. If false positives appear in practice, tighten by adding the ancestor "Learn more" check inside `detectListingHealth()` (single function, one place to fix).

**Rescan payload sends the DB-stored offer URL, not the tab's final URL.** `OfferIngestionService` matches the existing offer by exact `url`; Amazon redirects `/dp/ASIN` to slugged canonical URLs, so posting `tab.url` would miss the match and create duplicate offers. The worker walks `offer.url` from rescan-list and posts that same string back.

**Rescan `updated` counter includes server actions `refreshed|matched|created`.** For a work-list built from existing offers the action is essentially always `refreshed`; `matched`/`created` can only occur if the offer row was deleted mid-run — counted as updated rather than inventing a separate bucket.

**Unavailable listings are counted `skipped`, not refreshed.** `extractProductPageData()` early-returns `{unavailable:true}` before extracting a title, and `raw_title` is required by the ingest contract, so there is nothing trustworthy to POST. Consequence: a listing that went permanently unavailable keeps its stale data + old `health_checked_at`, so it keeps sorting first in future rescan lists. Proper handling is the spec's own future `unavailable` listing-flag (ListingHealth "room to grow") — deliberately not invented client-side now because the server wouldn't accept the flag (422 on unknown flags).

**SERP concatenated-title dedup was kept (B4 "untouched raw title").** `extractSerpProducts()` still collapses Amazon's DOM artifact where the hidden `.a-truncate-full` copy concatenates with the truncated copy ("Title…Title…"). That repair reconstructs the actual on-page title rather than cleaning it; removing it would ship garbage titles no human ever saw. No trimming/cleaning of the real title happens anywhere (`.trim()` of whitespace only). The pre-existing client-side skip of renewed/refurbished SERP cards was REMOVED per B4 — those cards are now sent with an explicit `condition` so the server flags them.

**`extractReviewsCount()` now returns `null` (never 0) and serves both SERP cards and product pages.** The SERP flow is unaffected (its `< 5` gate treats null like 0); the product-page flow previously coerced missing counts to 0, which the server would have stored — that was the B3 bug. Product-page strategies (`#acrCustomerReviewText`, `[data-hook="total-review-count"]`, `#averageCustomerReviews` aria-labels, reviews-anchor text) run before the card strategies because they're ID-anchored and can't false-positive from carousel widgets.

## Builder judgment calls — non-Amazon availability detection (extension v1.3), 2026-08-14

**Files:** `chrome_extension/content.js` (new `detectStoreAvailability()` + three extractors), `chrome_extension/manifest.json` (1.2→1.3), `docs/specs/029-extension-rescan-condition.md` (B1b + Phase B QA step 9).

**Reporting `condition: 'new'` for these stores is a deliberate, load-bearing choice — not a shortcut.** The alternative (send only `listing_flags`, no condition) does nothing at all: `ListingHealthService::apply()` returns immediately on a null condition, which is exactly the bug being fixed — 116 non-Amazon offers refreshing forever without a `health_checked_at` stamp. `unknown` was also rejected as the default: it is stamp-only server-side and explicitly does NOT clear `listing_flags`, so a product coming back in stock would keep a stale `unavailable` flag and stay pick-ineligible indefinitely. Only `new` reaches the clean branch that wipes flags. It is also honest: Clive/SCG/WLL are authorised dealers selling new goods, so "the page loaded and shows a normal new-goods listing" is a true statement about what the DOM shows. The trigger is deliberately narrow — a product title was found — and `unknown` is returned otherwise, so a partial/blocked page is never laundered into a clean bill of health.

**Deliberately did NOT attempt condition (renewed/refurb/open_box) or `high_price` for these stores.** These retailers don't sell refurbished goods through these product pages, so any DOM heuristic would produce false positives on a field whose negative values set `is_ignored = true` on the PRODUCT — the most destructive outcome in this system. `high_price` is Amazon's own first-party buy-box label; there is no equivalent signal on a Shopify storefront, and synthesizing one from price comparison is a server-side pricing question, not a DOM-scraping one. Silence beats a guess on both.

**Layered detection with a decisive first layer, because the selectors are unverifiable from here.** I cannot load clivecoffee.com or wholelattelove.com, so a single-selector implementation would be a coin flip that rots invisibly. Four independent layers, each able to fire alone: (a) JSON-LD `offers.availability`, (b) `product:availability`/`og:availability` meta, (c) add-to-cart button state, (d) scoped inventory/leaf text. Layer (a) is treated as **decisive when present** (short-circuits both ways) rather than merely additive: it is first-party structured data, and on a multi-variant Shopify product it is the only layer that can see that a sold-out variant sits alongside a buyable one. The rule "any purchasable variant ⇒ the product is NOT unavailable" is the right call for a price aggregator — the offer still exists and is buyable, even if the default-selected variant isn't. The recursive key-name walk (rather than a fixed `offers[0].availability` path) is what makes it survive `@graph`, `AggregateOffer`, and app-injected nesting.

**Two anti-false-positive guards worth naming, both driven by the asymmetry of the error cost.** A missed sold-out listing is the status quo (no worse than today); a FALSE `unavailable` flag actively removes a healthy, buyable product from landing-page pick eligibility. So: (1) **hydration guard** — a `disabled` add-to-cart button counts as sold out only when its label does NOT still read "Add to cart"/"Buy it now", because several Shopify themes render the ATC disabled until JS hydrates, and the rescan walk could easily photograph that moment; (2) **scope discipline** — layers (c) and (d) only run inside a product-form/product-info container, and when no such container is found they are skipped entirely rather than falling back to a whole-document scan, which would hit "Sold out" badges in related-product carousels. Both guards are covered by explicit fixtures.

**Price on a sold-out page: nulled ONLY when absent or `<= 0`, deliberately diverging from the Amazon path.** `extractProductPageData()` hard-nulls the price on an unavailable Amazon page because its fallback strategies scavenge stale meta tags and carousel prices that aren't the listing's price. Shopify-style stores are different: they normally keep displaying the real, current price while sold out, and it comes from the same scoped selector as the in-stock case. Nulling it would discard good data — and per the 2026-08-12 incident logged above, a flagged offer with a null price is precisely the shape that broke pick eligibility. So a genuinely displayed price survives; only a missing/placeholder value becomes `null`.

**Verified `popup.js`/`background.js` need no change rather than editing them.** Both POST paths spread/forward whatever `extractStoreProduct()` returns (`background.js` sets `payload.condition`/`listing_flags` for any store; `popup.js`'s non-Amazon branch spreads `{...product}`), both already strip an `unknown` condition per 029B-B3, and the tallies are correct as-is: an `unavailable` non-Amazon ingest returns `action: refreshed` (offer-level flags never set `is_ignored`, so `flagged_condition` is never returned), which `background.js` counts as `updated` — matching the spec's "counts as updated, not skipped" requirement. The only edit in those files would have been cosmetic, so none was made. One stale comment in `content.js`'s `RESCAN_EXTRACT` handler ("other stores omit them") was corrected.

**Testing gap the owner must close.** There is no JS test harness in this repo. I built a throwaway jsdom harness in the scratchpad (not committed — adding jsdom as a project dependency for one function was not in scope) and wrote 64 fixture assertions: all four layers, kebab-case/`OutOfStock`/`out_of_stock` spellings, schema.org token coverage (`PreOrder`/`BackOrder`/`LimitedAvailability` treated as purchasable, `InStoreOnly` as non-decisive), multi-variant JSON-LD both ways, malformed JSON-LD, the hydration guard, the carousel-badge and `<option>` false positives, full payload shapes for all three stores, and 4 Amazon `detectListingHealth()` regressions. All 64 pass. **This proves the logic, not the selectors** — every CSS selector was inferred from the existing extractors' patterns and standard Shopify/Dawn conventions, never confirmed against a live page. Phase B QA step 9 exists specifically to close this, and includes recording which layer *should* have fired if a real sold-out page comes back unflagged. Worth considering later: commit a small fixture-based JS test harness (jsdom + a handful of saved real product-page HTML files), which would make `detectListingHealth()`, `detectStoreAvailability()`, `conditionMarkerFromText()` and `extractReviewsCount()` genuinely regression-tested — the spec already notes they are pure functions written to be testable.

Three small, independently-readable copies over one parameterized one, consistent with the existing pattern in this codebase.

**Fix 3: changed `Product::bestPrice()` from an independent `offers->min('scraped_price')` to `$this->best_offer?->scraped_price`, beyond what the task explicitly named.** The task listed `best_price` as something that "derives from" `bestOffer`, but the code as found computed it independently (raw min across ALL offers, condition/flags-blind). Left as-is, a customer could see the CHEAPER excluded (refurbished/flagged) offer's price displayed while `affiliate_url` (already `best_offer`-derived) linked to a different, pricier clean offer — the exact "price shown, link elsewhere" mismatch bug in a different shape. Changed it to derive from the same `best_offer` so both always describe one offer. Audited every `best_price`/`estimated_price` reader afterward (list in the todo.md entry) to confirm none assumed the old raw-min behavior; none did.

**Two narrow-select eager loads needed a `condition`/`listing_flags` column fix, found only by reasoning through what "an unselected column resolves as" means for the new accessor logic.** `PriceTierRecalculator` and `SelectLandingPagePicks` both eager-load `offers` with an explicit column allowlist that omitted `condition`/`listing_flags`. Since Eloquent returns `null` (not an error) for an accessed-but-unselected column, `bestOffer`'s new exclusion (`!in_array(null, NEGATIVE_CONDITIONS)` is always true, `array_intersect([...], [] ?? [])` is always empty) would have silently evaluated every offer as "clean" in exactly those two code paths — the fix would have been dead on arrival for category-wide tier recalculation and (via the `image_url` accessor, which falls back to `best_offer`) landing-page pick image resolution. Fixed both selects; grepped the rest of the codebase (`grep -rn "offers:id,product_id"`) and confirmed no other narrow select feeds a `best_offer`/`best_price`/`image_url`/`affiliate_url`/`estimated_price` read.

**Deliberately left three callers unfixed, all pre-existing/out-of-scope, not caused or worsened by this change:**
1. `ProductCompare::scoredProducts()` computes its own `offers->min('scraped_price')` for ranking/the price filter slider (a perf-cached raw-array path, explicitly NOT the Eloquent accessor). A bad-condition offer could theoretically bias a product's rank/filter membership by price alone. Left alone per the standing Spec 029 §A2 precedent for `high_price` ("Compare pages unchanged for now … revisit if CTR data says otherwise") — the displayed cards on that page use `price_tier` (a separately-stored integer, itself fixed via `PriceTierRecalculator`) and the real `affiliate_url` accessor, not this raw price, so no customer-facing link mismatch results from leaving it.
2. `Filament\Resources\ProductResource` and `Filament\Pages\ProblemProducts` both intentionally show a raw `offers->min('scraped_price')` for admin visibility into ALL offer data (including bad listings, which is the point of an admin review tool) — not accessor-based, not customer-facing.
3. `App\Console\Commands\FlagConditionProducts`'s second query block (`--urls` review mode) selects `offers:id,product_id,store_id,url` (no `scraped_price` at all) yet displays `$product->estimated_price` — this was ALREADY silently null before this change (an unselected column resolves as null regardless of any accessor logic); confirmed by re-reading the pre-fix accessor, which would have hit the same `->offers->min('scraped_price')` on an empty column. A genuinely pre-existing, unrelated display bug — noted here rather than opportunistically fixed, since it's outside this task's three named holes.

**Testing gap unchanged and still owner-owned.** There is still no committed JS test harness; I rebuilt the throwaway jsdom harness in the scratchpad (25 assertions, all passing) and did not add jsdom as a project dependency. **These fixtures prove the marker logic, not the live selectors** — I cannot load wholelattelove.com, so the product-type/badge/breadcrumb selectors remain inferred from standard Shopify/Dawn conventions. The title path, which is the one that actually matters for the known QA case, depends on no new selector at all (the extractors already extract the title successfully today), so it is the least likely of the three to need live correction. Phase B QA step 10 pins the confirmation: single-scan the Refurbished Lelit Anna URL and expect `condition = refurbished`, plus one ordinary WLL machine expecting `new` to prove the marker doesn't over-fire. The standing recommendation from 2026-08-14 stands and is now stronger: commit a small jsdom fixture harness with saved real product-page HTML.

## Builder judgment calls — picks-only rescan mode, Chrome extension v1.5 (Spec 031 T2), 2026-08-16

**Files:** `chrome_extension/{popup.html,popup.js,background.js,manifest.json}`. No `app/` or `tests/` files touched — the server half (T1) was built in parallel by another agent.

**Contract gap found before writing code, and handled by failing fast rather than silently.** `/api/extension/ingest-offer` validates `category_id` as `required` (`OfferIngestionController::ingest()`), and the walk POSTs one refresh per offer. In category mode the popup supplies the selected category for the whole run; a picks run spans categories by definition and has no selector, so each row must carry its own `category_id` — but neither the contract I was given nor `picksScopeOffers()` as landed returns one. Three options considered: (1) send `category_id: null` and let the server 422 ~100 times (~17 min of wasted page loads per run, and the failure would read as a network/scrape problem rather than a contract bug); (2) look the mapping up client-side (no endpoint exposes product→category; `/api/categories` returns categories only); (3) code to `offer.category_id ?? rescanRun.categoryId` and **preflight** the work list, refusing to start with the message *"Server returned N pick(s) without category_id — the picks list must include it."* Chose (3): it costs one line on the server (`picksScopeOffers()` already joins the product to resolve slugs), it names the exact fix in the popup rather than in a console, and the `??` means the day the field appears the extension just works with no further change. Logged as an open **T1 follow-up** in Spec 031's task breakdown and as a contract addendum in the spec body, since T1 is otherwise marked done.

**Parameterised the existing walk; resisted every temptation to branch inside it.** The instruction was explicit about not forking, and the risk is real — `background.js`'s correctness rests on invariants (exactly one armed listener + watchdog, one generation counter consumed exactly once per offer, advance-never-while-paused) that a second copy would drift from. So `scope` is stored on the run object and read in exactly four places: the `startRescan()` initialiser, two progress strings, and `runLabel()`. Everything else is scope-blind. In particular `noteFlaggedGuide()` keys off the presence of `offer.landing_page_slug`, which category rows simply do not have, so it is a no-op in category mode **without** an `if (scope === 'picks')` guard. Same on the popup side: one `beginRescanRun(scope)` serves both buttons, and one progress panel serves both runs.

**`flagged_guides` is deliberately broader than the `flagged_condition` counter it sits beside.** The counter only increments on the server's `flagged_condition` action; the spec's response rule fires on *any* bad-listing signal on a pick ("condition, high_price, or unavailable"). So the guide tally also fires on `skipped_condition` (a condition-marked listing on a live pick is exactly the case the pass exists to catch) and on `high_price`/`unavailable` read from the DOM we just scraped — the server stores those flags without changing `action`, so they are invisible to the counter. The flags are read off the **payload**, not the raw extraction: on an unverified page (029B-B3's `'unknown'` condition) the flags are deliberately withheld from the server, so they are not a health observation and must not name a guide either. I did **not** fix the counter itself: "the popup flag-tally undercount" is named in Spec 031's own out-of-scope list, and widening it would change category-rescan reporting that nobody asked me to touch. The two numbers can therefore disagree (e.g. `flagged 0` next to `flagged: gaming-chat-headsets`); that is intended, and the guide line is the actionable half.

**A guide is named once per flagged *offer*, not deduplicated per product.** A product with two flagged store listings increments its guide twice, rendering as `gaming-chat-headsets (2)`. Since the picks list returns every offer of every pick product (by design — `best_offer` moves between stores), a per-offer count is the honest reading of "how many bad listings back this guide's picks", and the owner's action (rescan that category) is the same at 1 or 2. The server's own tie-break means a product picked on two guides is attributed to only one of them (first slug alphabetically), so a cross-listed pick names one guide, not both — accepted, since the response is a category rescan and both guides share the product either way.

**Amber, not green, when guides are named.** The end-of-run line previously always rendered `.success` green. A picks run that ends "complete: updated 98 · flagged 2 — flagged: usb-mics" is not a success in the sense the owner cares about, so a new `.warn` class (`#b45309`) is used whenever any guide is named, on both the finish and the manual-Stop paths. This is the only change to category-rescan-visible behaviour, and it only fires in a case that could not previously occur (no slugs, no warn).

**Pause/Resume/Stop button labels shortened from "Pause Rescan"/"Resume Rescan"/"Stop Rescan" to "Pause"/"Resume"/"Stop",** and the two status strings they set genericised, because the same three buttons now drive both modes and mode-specific text on a shared control would be wrong half the time. The mode is already stated one line above them in the progress label.

**Verification I could and could not do.** Could: `node --check` on all three JS files, `manifest.json` parses at 1.5, and every DOM id `popup.js` references exists in `popup.html` (checked by diffing the id sets — this is the failure mode a syntax check misses). Could not: anything requiring Chrome or the network. There is still no committed JS test harness, and unlike the v1.3/v1.4 extractor work this change is not fixture-testable — it is chrome.* messaging, tab lifecycle, and service-worker restart behaviour, which need a real browser rather than jsdom. So the walk's shared invariants are argued from the fact that they are *literally unmodified*, not from a passing test. The live run is owner QA (Spec 031, "Owner QA — Verify Live Picks"), and it cannot pass at all until the `category_id` follow-up above lands.

## Builder judgment calls — tenant picker (`GET /api/extension/tenants` + extension v1.6), 2026-08-16

**Files:** `app/Http/Controllers/Api/TenantListController.php` (new), `routes/api.php`, `tests/Feature/ExtensionTenantListTest.php` (new), `chrome_extension/{popup.html,popup.js,manifest.json}`. Both halves built together so the contract cannot drift.

**Security posture, stated explicitly rather than left implicit.** This endpoint hands the full list of tenant ids to any holder of the extension token. That is not new exposure: the same token already grants full read/write on *any* tenant simply by setting the `X-Tenant-Id` header (`InitializeTenancyFromPayload` does `Tenant::find()` on whatever it is given, with no relationship between the token and the tenant), so the only thing an attacker gained here is not having to guess ids — and ids are already semi-public, appearing in the `/api/categories` flow the token holder can drive anyway. What I *did* tighten: the response carries `id` and `name` and nothing else. `Tenant` keeps branding/settings in a `data` JSON column via VirtualColumn, and returning the model wholesale would have leaked all of it; a test asserts the exact key set is `['id', 'name']` so a future `->toArray()` refactor trips a red test rather than shipping the `data` column. The real standing risk is unchanged and out of scope for this task: the extension token is a single shared secret with no per-tenant scoping.

**No `orderBy('name')`; ordered by the string actually displayed.** The instruction said "ordered by name (or id if name is null)". `tenants.name` turns out to be a `NOT NULL` string column (`2019_09_15_000010_create_tenants_table.php`) and a real custom column (`Tenant::getCustomColumns()` returns `['id', 'name']`), so the null case cannot arise from the schema — but an empty string can. Rather than sort by one string and display another (which produces a select box that is visibly out of order in exactly the rows where the fallback fires), both the sort and the label use `COALESCE(NULLIF(name, ''), id)`. Single-quoted `''` deliberately, so the expression is valid on both MySQL and the test suite's sqlite connection; a double-quoted `""` would be read as an identifier under sqlite. I did **not** reach into `data->brand_name` as a secondary label source: `name` is the guaranteed-present human label, `brand_name` is optional storefront branding, and preferring a sometimes-absent field over a mandatory one would make the list less predictable, not more.

**Its own route group, and a comment saying why.** The obvious-looking edit — adding the route to the existing 60/min extension group — would have broken it outright, because that group carries `InitializeTenancyFromPayload` and the whole point is to work *before* a tenant id exists. So it gets a two-line group of its own with the same `throttle:60,1` as its read-only siblings, plus a comment in `routes/api.php` explaining the omission. Without that comment this reads as an oversight and the next person "fixes" it. Two tests defend it from the other direction: one proves a request with **no** `X-Tenant-Id` returns 200 (behind the middleware it would 422), and one proves an **unknown** `X-Tenant-Id` is ignored rather than 404ing "Invalid tenant." — that second case is the one that would lock the owner out of the very list they need to correct a stale saved id.

**The list never overwrites the saved tenant id — the invariant the whole client design hangs on.** A tenant picker that clears `chrome.storage.local.tenantId` when the fetch fails would silently break every scrape while offline, on the wrong environment, or against a server predating this route. So `renderTenantOptions()` only ever *reads* `TENANT_ID`; the sole write is the explicit `change` handler. When the saved id is absent from the returned list (fetch failed, wrong env, tenant deleted) it is re-inserted as a selected `"<id> (saved)"` option, so the popup always shows what the headers are actually sending rather than falling back to a blank box that misrepresents live state. `TENANT_ID` therefore remains the single source of truth and all ~8 existing `X-Tenant-Id` fetches are untouched.

**No auto-select of the first tenant when nothing is saved.** Tempting (one less click on a fresh install) and rejected: this select box decides which tenant every subsequent import writes into, and defaulting it means a fresh install can silently write products into whichever tenant happens to sort first. The empty state is a `disabled` "Select a tenant..." placeholder, which costs one deliberate click exactly once.

**Skipped the manual-entry fallback, deliberately.** It was offered as optional "if genuinely simple", and it is not worth its cost here. The degradation path already preserves and displays the saved id, so the only scenario a text box would serve is *first-ever setup against a server too old to have this route* — which cannot happen, since both halves ship together. Keeping a second input would also reintroduce the exact typo-prone free-text flow this change exists to remove, and would need its own precedence rules against the select. The inline hint names the actual fix instead ("check your API token" / "server unreachable").

**Failure messages are inline and quiet, not `showError()`.** Before a token is saved the endpoint is *expected* to 403 — that is a normal first-run state, not an error. Routing it through the shared `#status` line would put a red error in front of the owner on every fresh popup open and would fight with whatever scrape status is already there. A dedicated `#tenantHint` line under the select carries it, distinguishing the three cases the owner can act on differently: no token yet, 403 (bad token), and unreachable/other HTTP status. The list is refetched on token save and on environment switch, since each environment has its own tenant table.

**Verification I could and could not do.** Could: full `php artisan test` (594/19 → **604 passed / 19 skipped**, +10 new, no regressions), `node --check` on all three extension JS files, `manifest.json` parses at 1.6, and — the check a syntax pass misses — a set-diff of every `getElementById()` in popup.js against every `id=` in popup.html, confirming no stale reference survived removing `tenantInput`/`saveTenantBtn` (their only remaining mentions in the tree are inside an explanatory comment). Confirmed no new manifest permissions are needed: the call goes to `${baseUrl}`, i.e. `127.0.0.1:8003` or `pw2d.com`, both already in `host_permissions`. Could not: exercise the popup in Chrome — no committed JS harness, and this change is `chrome.storage`/`fetch`/DOM wiring that needs a real browser. The rendering paths (populated list, empty list, 403, network failure, saved-id-not-in-list) are argued from code, not from a passing test; the first live popup open is owner QA.
